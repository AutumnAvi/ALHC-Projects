# ALHC Projects — architecture source of truth

ALHC's own Asana-style work platform. The product is generic: **Workspace → Project → Section → Task → Subtask**, with tasks able to live in several projects, **portfolios** grouping projects for cross-project progress, rules that can post to Slack or call outbound webhooks, an importer for Asana export files, multi-select bulk edits with Asana-style keyboard shortcuts, project / task templates plus Duplicate project on one copy engine, workspace admins, comment editing / reactions / @mention autocomplete with an archivable Inbox, personal My Tasks sections, a Workload view per project and portfolio, a workspace Teams directory with group invites, Asana-style goals with sub-goals and progress, a read-only critical path with slack on Timeline, portfolio depth (nested portfolios, portfolio custom fields, a portfolio Timeline, project status history), task types (milestones, approval tasks on the approvals engine) with workload and goal progress rolled up through nested portfolios, real subtasks (subtasks are tasks with a parent, nested up to 4 levels, living in their top-level task's projects), workspace reporting (Reports page, all-projects report, personal dashboards) with CSV export and print-friendly pages, native workspace tags, project Messages (threads with replies, @mentions, and reactions), inline attachment previews, scheduling depth (dependency lag and start-to-start links across projects and subtasks, confirmed auto-shift of dependents with Undo, converting tasks to subtasks and back), daily essentials (private My Tasks tasks with no project, Duplicate task, archived projects, task likes, auto-shift from bulk due dates and Workload with an optional pull-earlier), integration depth (Slack Block Kit task cards and a `{task_link}` token, HMAC-signed outbound webhooks, a per-project delivery log with capped exponential retry), inbound integrations (per-project inbound webhook endpoints that create tasks from outside, with hashed one-time-shown tokens, optional HMAC signatures, idempotency, a call log, and a rule trigger), and live email (delivery within a minute through a pg_cron + pg_net kick, live sent / failed status on activity and in Deliveries, form submitters following their request, comment emails to followers with a per-person toggle, and reply by email through Resend inbound), Asana-style people and workspace administration (required teams with a default team, public-to-team projects people can browse and join, workspace members invited by email with pending project / portfolio / team invites before first sign-in, removal that keeps the person's work, and a workspace settings console), an Asana-style shell (a dark top bar with a global Create menu and a search palette, a dark sidebar with Starred projects, blue primary color, colored value pills, and a Settings modal), an Asana-style project page (a header with a status menu, member avatars, and a Share dialog; an Overview tab; a one-line toolbar with an Options menu; List column menus and row details; a polished Board), an Asana-style task pane (next to the list at about 45% of the content width, header actions and a "…" menu, a two-column field grid, a calendar date picker with start date, time, and Repeats, attachment cards, Comments / All activity tabs, a compact comment and collaborators footer, and a full-screen view), and Asana-style create flows and Customize (a full-screen template gallery for new projects, dialogs for new portfolios and goals, a Browse projects table, a Customize panel with a view per area, a form editor with a live preview and Email / Heading questions, a full-page rule canvas with Else if / Otherwise branches, and a fields list with an Edit field modal, field descriptions, a workspace field library, and change notifications), and an Asana-style Inbox, Home, Teams, and Admin console (an Inbox with Activity / Bookmarks / Archive / @Mentioned tabs, filters, and day-grouped cards; a Home with a greeting and My tasks / Projects / People widgets; team pages with Overview, curated work, Members, All work, Messages, and Calendar tabs; a separate Admin console for workspace admins; and a Settings modal with Email forwarding), and real features for invites and email-in (invites by email on projects, portfolios, and teams that email the invitee and join them on first sign-in, workspace admins inviting new addresses, Resend / Cancel; a personal forwarding address that turns emails into tasks with their attachments; attachment questions on public forms; team pages that preselect their team; Home's inline Create task row). Team-specific workflows (e.g. Autumn Lake Creative Requests) are built *on top of* this model later; never bake one workflow into the schema.

## Stack

- Next.js 16 App Router, React 19, TypeScript strict, Tailwind CSS 4 (`src/` layout, app at repo root)
- Supabase Auth (email + password for now; Google OAuth is the long-term method) + Postgres + RLS via `@supabase/ssr` / `@supabase/supabase-js`
- Deployed on Vercel; `vercel.json` only declares the daily workflows cron
- Email through Resend's HTTP API (no SDK), mocked when not configured; replies come back through Resend inbound (`email.received` webhook → `/api/inbound/email`)
- Delivery within a minute: pg_cron job `alhc-delivery-kick` asks the app to drain through pg_net (URL + secret in Supabase Vault); the database still never sends anything itself
- Slack incoming webhooks and outbound HTTPS webhooks (rule actions) through the same outbox → app drain pattern; the database never makes HTTP calls
- Inbound webhooks (`/api/inbound/[token]`) call one anon-callable database function with the anon key — never the service role
- npm (`package-lock.json` is the lockfile)

## Auth model

1. **Interim: email + password.** `/login` posts to the `passwordAuth` Server Action (`src/app/login/actions.ts`). Sign in runs `signInWithPassword`. Sign up runs `signUp` with `emailRedirectTo` set to `/auth/callback`, so the confirmation link lands there. Supabase's Email provider must be on with **Confirm email** enabled: confirmation proves inbox ownership, and `is_allowlisted()` ignores unconfirmed users. Accounts can also be created in the dashboard (Auth → Users → Add user, auto-confirm).
2. **Later: Google.** `signInWithOAuth({ provider: "google" })` → Google → `/auth/callback`. The button (`login/google-sign-in-button.tsx`) is hidden unless `AUTH_GOOGLE_ENABLED=true`. Turn it on once the Supabase Google provider is configured (README "Setup: Google OAuth"). Google remains the intended long-term method.
3. Every path ends at the same gate. The callback exchanges the code, and `passwordAuth` uses the session it just created. Both then call `rpc("is_allowlisted")`. Not allowlisted ⇒ `signOut()` and redirect to `/denied` — a rejected user never keeps a session.
4. `(app)/layout.tsx` calls `requireMember()` on every render: no user ⇒ `/login`; user removed from the allowlist ⇒ `/auth/denied` (signs out).
5. RLS is the real boundary. `public.is_allowlisted()` (SECURITY DEFINER) is true only when `auth.uid()` maps to an `auth.users` row with a confirmed email present in `public.allowed_emails`.
6. **Inner gate: project membership** (Teams & permissions). The allowlist decides who can have a session; `project_members` decides which projects that session can read or change, and with which role. Every role helper also requires `is_allowlisted()`, so de-allowlisting someone revokes all project access at once. Project pages 404 for non-members (`(app)/projects/[projectId]/layout.tsx` checks `getProjectRole()`), and the home page, sidebar, My Tasks, search, and Inbox only ever show projects and tasks RLS lets the viewer read.

7. **Workspace admins** (`workspace_admins`, `is_workspace_admin()`) are a workspace-level role, not a third gate: they manage workspace templates and see past imports of projects they can already read. **A workspace admin gets no access to private project contents** — no project-scoped policy checks `is_workspace_admin()` to grant reads or writes, so project access still comes only from `project_members`. See “Workspace admin and comments model”.

8. **Teams** (`teams`, `team_members`) are a workspace directory, not a gate either: **a team never grants project access** by itself (since Asana feel, batch 2 its members may *join* the team's public projects — see item 18). No project-scoped policy or helper reads `team_members`; the group invite (`add_team_to_project`, Project Admin+) only calls `add_project_member()` per person, so access still comes from ordinary `project_members` rows. See “Goals and Teams directory model”.

9. **Nested portfolios** (`portfolio_children`) never grant access either: a parent's members see a nested portfolio only if they are its Viewers+, and every rollup (report, progress, timeline, workload, goal progress) still filters each project through `has_project_role(project, 'viewer')`. See “Critical path and portfolio depth model” and “Task types and nested rollups model”.

10. **Subtasks** (`tasks.parent_task_id`) resolve to their **root task's** projects — never broader, never their own memberships (they have none). `profile_task_role()` reads the root's memberships, so every `has_task_role` policy (comments, followers, attachments, field values, approvals) follows the root, and losing the root's project means losing its subtasks. See “Real subtasks model”.

11. **Reports** (Reporting and export) never widen access: every report RPC is SECURITY INVOKER and checks `has_project_role(project, 'viewer')` per project; projects a person can't read are only ever a count (`workspace_hidden_project_count`), and workspace admins get no extra rows. CSV export reads with the signed-in user's client. See “Reporting and export model”.

12. **Tags and Messages** never widen access either: tag names are workspace-level (allowlisted read), but `task_tags` links follow the task (`has_task_role`, subtasks through their root), and `project_messages` follow the project (`has_project_role`); a workspace admin manages tag metadata only and reads no task links or messages of projects they aren't in. See “Tags and collaboration model”.

13. **Dependencies** need read access to **both** tasks to be seen (`task_dependencies_select_viewer` = `has_task_role` viewer on predecessor and successor), and Editor on both to be added, changed, or removed — across projects too; auto-shift and task ↔ subtask conversion run as the caller through RLS. See “Scheduling depth and polish model”.

14. **Private tasks** (`tasks.home_project_id` null, Daily essentials) are readable and editable by their top-level task's **creator and current assignee only** (`profile_task_role`), subtasks through their root. Nobody else — workspace admins included — can read, find, follow, be @mentioned in, or be notified about one. Adding one to a project makes it an ordinary task of that project. See “Daily essentials model”.

15. **Archived projects** (`projects.archived_at`) are read-only for everyone: every membership counts as **Viewer** in `profile_project_role` / `profile_task_role`. Reading is unchanged (members only; workspace admins get nothing). See “Daily essentials model”.

17. **Reply by email** (`/api/inbound/email`, Email live) is a fourth public entry point, verified by Resend's webhook signature. Its write goes through `post_email_reply` (SECURITY DEFINER, **service_role only**), which posts only for the reply token's person, from that person's own address, while they are still allowlisted and a Commenter+ on the task. Comment emails only ever go to followers who can read the task, checked when queued and again when sent. See “Email live model”.

16. **Inbound webhooks** (`/api/inbound/<token>`) are a third public entry point next to public forms: no session, the anon key, and one SECURITY DEFINER function (`receive_inbound_webhook`) that only ever writes into the endpoint's project **as the endpoint's creator**, and only while that person is still an allowlisted Editor+ there. Endpoints and their log are Admin+ of the project through `has_project_role` (workspace admins get nothing). See “Inbound integrations model”.

18. **Workspace members** (Asana feel, batch 2): workspace admins add and remove allowlist entries in the app through definer RPCs (`invite_to_workspace`, `resend_workspace_invite`, `remove_workspace_member`); nobody writes `allowed_emails` directly. Removing sets `allowed_emails.removed_at`, which every allowlist check ignores (`is_allowlisted`, `profile_is_allowlisted`, `profile_in_workspace`, `sync_profile_for_user`, the invite RPCs), so sign-in stops while the profile, work, and memberships stay; adding the email back restores access. Invites to projects, portfolios, and teams for people who haven't signed in yet are `pending_memberships` rows applied on their first **confirmed** sign-in (`apply_pending_memberships`). **Public-to-team projects** (`projects.visibility = 'team'`) let members of the project's team find and join them (`browse_projects` / `join_project`, Editor) — the only way a team relates to project access; no read policy consults visibility or teams, and private projects stay invisible to non-members, workspace admins included. See “Asana feel model (batch 2)”.

19. **The search palette and stars** never widen access either (Asana parity, batch 1): the palette's results and recents come from server actions on the person's own client (RLS; tasks through `search_tasks`), and stars are own rows that only show for projects the person can still read. Workspace admins get nothing extra. See “Asana parity model (batch 1)”.

20. **Share** (Asana parity, batch 2) is a new door to the same rooms: it reads with the person's own client (`loadProjectShare`) and changes access only through the existing actions and RPCs (`add_project_member`, `add_team_to_project`, `update_project_member_role`, `remove_project_member`, `updateProjectTeam`, `cancelPendingInvite`), so their Admin+ / owner checks apply unchanged and a workspace admin gets nothing they didn't have. See “Asana parity model (batch 2)”.

21. **The field library and Browse projects' people** (Asana parity, batch 4) never widen access: `list_field_library()` returns only definitions someone published with “Add to field library” (name, type, description, options — never the project's name or id), and `browse_project_people()` adds owners, members, and a last-modified time to exactly the rows `browse_projects()` returns. Field-change notifications go through `notify_with()`, so only followers who can read the task hear about it. See “Asana parity model (batch 4)”.

22. **The Admin console, curated work, and bookmarks** (Asana parity, batch 5) never widen access either: `/admin` is a separate page that 404s for everyone but workspace admins (`requireWorkspaceAdmin()`), and it only shows what an admin could already read (the allowlist, teams, tags, invite emails, their own projects' deliveries) plus one definer RPC, `list_workspace_member_activity()` (workspace admins only: each allowlisted address's last sign-in time — nothing about projects or tasks). A team's curated work (`team_curated_work`) shows an item only to people who can open its project or portfolio, so a curated private project stays invisible to the team's other members and to workspace admins. Inbox bookmarks are the recipient's own column on their own items. See “Asana parity model (batch 5)”.

23. **Invites, forwarding, and form uploads** (Real features 1) never widen access either. Inviting by email still needs the project / portfolio Admin+ or team-manager role by the inviter's own membership; only a workspace admin's invite can put a new address on the allowlist (through `invite_to_workspace`), and a workspace admin still can't invite anyone into a project they don't administer. Invite emails name their project, portfolio, or team, so the outbox shows them only to the people who manage that invite (`can_manage_pending_invite`), never to workspace admins as such. A forwarded email becomes a task only for the forwarding token's own person, from their own address, while they're allowlisted, and only in a project they can still add tasks to (else their private task). Public form submitters upload as **anon** through one Storage insert policy (`alhc_storage.form_upload_allowed`, not callable as an RPC): only into the folder of a response that isn't a task yet, of an open form with a file question, within per-response, per-form, and daily caps; anon reads nothing back, the files become readable only once they are the new task's attachments (its readers, through the narrowed Storage read policy), and the cron route removes the rest after a day. A workspace admin's invite never restores someone removed from the workspace (that stays Admin console → Add back).

Allowlist entries are managed by workspace admins on Settings → Workspace → Members (or, for the first people, in SQL) — members cannot write the allowlist through the API.

- **Single workspace this phase:** migration seeds workspace `00000000-0000-4000-8000-000000000001` ("ALHC"); the app uses the oldest active workspace.
- **Profiles** mirror allowlisted auth users (name/avatar from Google; password users fall back to their email) via triggers on `auth.users` and on `allowed_emails` inserts. Assignees reference `profiles.id`.
- **Multi-homing:** `task_projects (task_id, project_id)` is the membership join. Section and `sort_order` live on the membership, so one task can sit in different sections/positions per project.
- **Home project rule:** `tasks.home_project_id` is the project the task was created in (its primary project); it is **null only for a private task** (and its subtasks), which has no memberships at all — adding it to a project sets that project as its home (`task_projects_10_adopt_private`), and a project task can't be made private. A trigger guarantees an active membership in the home project; removing the home membership is rejected — make another membership the home first. `tasks.workspace_id` always follows the home project.
- **Ordering:** fractional `double precision sort_order` (step 1024, midpoint inserts). No reindexing yet.
- **Soft delete only:** every content table has `deleted_at`. There are **no DELETE policies**, so hard deletes through the API affect zero rows. Reads in `src/lib/data.ts` always filter `deleted_at IS NULL` (the one exception is `listTrashedTasks()` for the Trash page); RLS intentionally does not, so restore works. Since Task depth, a soft-deleted **task** is readable only by Editors+ of one of its projects (`tasks_select_viewer`), and `rpc("restore_task")` brings it back (see “Task depth model”). Soft-deleting a section moves its tasks to "No section" (trigger). Soft-deleting a task hides it from every project and trashes its active subtasks with the same timestamp (restoring the task restores exactly those).
- **RLS policy pattern (since Teams & permissions):** project-scoped tables use `<table>_<command>_<minimum role>`, e.g. `tasks_select_viewer`, `tasks_update_editor`, `rules_insert_admin`, checked with `(select public.has_project_role(project_id, '<role>'))` or, for rows that hang off a task, `(select public.has_task_role(task_id, '<role>'))`. Author/recipient-owned rows add `_own` (`comments_insert_own_commenter`, `task_attachments_insert_own_editor`, `inbox_items_select_own_viewer`). Workspace-level tables keep the allowlist pattern: `profiles_select_allowlisted`, `profiles_update_own`, `allowed_emails_select_allowlisted` (read-only), `workspaces_select_allowlisted`, `rule_presets_select_allowlisted`, `projects_insert_allowlisted` (anyone allowlisted can start a project and owns it), and `portfolios_insert_allowlisted` (same for portfolios). Portfolio tables use `has_portfolio_role` (see “Portfolios and reporting model”). Integration tables hold secrets and have RLS on with **no policies and no client table grants** (see “Integrations model”). See “Teams & permissions model” for the full matrix.
- **Dates:** `tasks.due_on` and `tasks.start_on` are plain `date`s. Both are optional; when both are set, `start_on <= due_on` (constraint `tasks_start_on_before_due_on`; `updateTask` turns a violation into “The start date must be on or before the due date”). Only Timeline reads `start_on`; Calendar, My Tasks, every filter (`due` kinds, including “No due date”), rules (`due_approaching`), and forms (`maps_to: due_on`) stay on `due_on`. Optional **times** (`due_at` / `start_at`, Task depth) never replace the dates: a trigger keeps each `_on` equal to its `_at`'s local date in `tasks.time_zone`, so all day-based code is unchanged.
- **Task creation** goes through `rpc("create_task", { target_project, target_section, task_title })` so the task row and its home membership land in one transaction (and `workspace_id` is filled by trigger). Subtasks go through `rpc("create_subtask", { parent_task, task_title, before_task })` (no membership; root / home / workspace come from the parent). Private My Tasks tasks go through `rpc("create_private_task", { task_title })` (no project, assigned to the caller).

## Collaboration model

- **Activity is trigger-written.** `task_stories` rows (`created`, `completed`, `reopened`, `renamed`, `deleted`, `restored`, `assigned`, `unassigned`, `due_changed`, `start_changed`, `section_changed`, `project_added`, `project_removed`, `attachment_added`, `field_changed`, `recurrence_changed`, `recurrence_spawned`, `dependency_added`, `dependency_removed`, `integration_queued`, `integration_failed`, `kind_changed`, and since Scheduling depth and polish `dependency_changed`, `tag_added`, `tag_removed`, `converted_to_subtask`, `converted_to_task`) are inserted by SECURITY DEFINER triggers; clients can only read them. Membership changes made in the same transaction that created the task (`tasks.created_at = now()`) are not logged, so new tasks get one `created` story. `data` holds name snapshots (section/project/field names) so history survives renames.
- **Comments** (`comments`) are plain text, author = `auth.uid()` (enforced by policy), soft-deleted by their author only. Soft-deleting a comment marks its inbox items read (`comments_after_soft_delete`) and `listInbox()` hides them; the pane keeps a “Comment deleted” placeholder in its place (the body isn't sent to the browser). Authors edit the body only (`comments_05_guard_update`; `edited_at` marks it, shown as “(edited)”); see “Workspace admin and comments model” for edits, reactions, and @mention autocomplete.
- **@mentions are parsed in the database** by the `comments_after_insert` trigger: `@Full Name` or `@emaillocalpart` (case-insensitive, word-bounded) of an allowlisted profile who can read the task (a member of one of its projects). Matches become `comment_mentions` rows; the author is never mentioned.
- **Followers** (`task_followers`, soft delete) — auto-follow on: creating a task, being assigned, commenting, being @mentioned. Commenters and above can follow/unfollow from the pane; a follower must be able to read the task (`follow_task()` and the insert policy skip/reject anyone who can't).
- **Inbox** (`inbox_items`) is fan-out on write by triggers; clients can't insert. Kinds: `assigned` (to the new assignee), `mention` (to each mentioned person), `comment` (to every other follower not already mentioned), `completed` (to followers), plus `approval_requested`, `approval_decided`, and `rule` from Workflows (`data` jsonb carries status/note/message and the rule name). Since Asana parity, batch 4 a field with “Notify collaborators when changed” sends its followers `rule` items with `data.field_change = true` (field id / name, `value_text`, `message`), shown as “changed <field> on …”. Since Tags and collaboration extras an item can be about a project message instead of a task (`task_id` null, `message_id` set; kinds `mention` and `message`), written by `notify_message()` (see “Tags and collaboration model”). The actor never notifies themself, and nobody is notified about a task they can't read (`notify_with()` skips them). Recipients can only read their own items, and only while they can still read the task, and the column grant only lets them update `read_at`, `archived_at`, and (since Asana parity, batch 5) `bookmarked_at`. Inbox items never send email; only workflow emails do (see Email).
- **Append-only tables** — `task_stories`, `comment_mentions`, `inbox_items`, and `task_field_values` have no `deleted_at` (nor do `my_task_placements`, one row per person and task that is moved by update, `project_status_updates`, an immutable status log, and `portfolio_field_values`, cleared with JSON `null` like task field values): stories are an immutable log, mentions are derived from a (soft-deletable) comment (an edit only adds mentions), inbox items are dismissed by `read_at` and put away by `archived_at`, and a field value is cleared by writing JSON `null`.
- **Custom fields** are defined per project (`custom_fields`: `text`, `number`, `date`, `boolean`, `single_select`, `multi_select`, `people`). Select options live in `options` as `[{ id, name, color }]`; values (`task_field_values.value` jsonb) store option ids, so renaming an option never rewrites values. The `task_field_values_validate` trigger enforces the shape per type, that option/profile ids exist, and that the task is in the field's project. `show_in_views` pins a field as a List column and a Board card chip.
- **Section-bound status** (`bound_to_sections = true`, single-select only, at most one per project): the field has no stored values — its options are the project's sections and its value is the task's section in that project. Editing it in the pane calls `moveTask`. This is the native "status ↔ section" bind; there is no rule engine syncing two sources of truth.
- **Attachments** — files live in the private Storage bucket `task-attachments` at `<task_id>/<uuid>-<safe name>`; `task_attachments` holds metadata (soft delete) and `storage_path` must start with the task id. Browser uploads go straight to Storage (policy `task_attachments_objects_insert_allowlisted`), then `registerAttachment` records metadata. Downloads go through `/attachments/[id]`, which checks the metadata row via RLS and redirects to a 60-second signed URL. Since Tags and collaboration extras, PNG / JPEG / GIF / WebP show as pane thumbnails with a lightbox and PDFs open in the browser's viewer: the route serves inline only when `previewKind()` agrees for the file name, the recorded type, and the type Storage reports for the object (`info()`), else it forces a download — SVG and HTML always download. Limit: 25 MB per file (bucket `file_size_limit`, DB check, and client check). Storage objects are not deleted when an attachment is removed.
- **Search** — `rpc("search_tasks", { query, max_results })` (SECURITY INVOKER, so RLS applies) does escaped ILIKE over task title and notes (and, since Tags and collaboration extras, the names of the task's active tags), backed by `pg_trgm` GIN indexes. Results are ordered open before completed, then title matches, then notes matches, then tag-only matches, then most recently updated (max 100).
- **Realtime** — `comments`, `task_stories`, `inbox_items`, (since Workspace admin and comments) `comment_reactions`, (since Tags and collaboration extras) `project_messages` and `project_message_reactions`, and (since Daily essentials) `task_likes` are added to the `supabase_realtime` publication when it exists. The task pane and Inbox call `useRealtimeRefresh`; the sidebar badge refetches its count on change. Everything degrades to server-rendered data plus a 60 s poll / window-focus refetch for the badge when Realtime isn't available.

## My Tasks

`/my-tasks` lists open tasks assigned to the viewer across every project (`tasks.assignee_id`), labelled with the home project — subtasks included (labelled with their root task's project and “in <parent>”), and private tasks (labelled **Private**). The **Add task** box at the top creates a private task assigned to the viewer (`create_private_task`; see “Daily essentials model”); it lands at the top of Recently assigned. By default they sit in the viewer's own **sections** (see “My Tasks and workload model”); the **Due dates** toggle (Segmented control, remembered in the `my_tasks_layout` cookie) switches to Asana's due-date buckets, computed in the browser against the viewer's local date:

1. **Overdue** — due before today
2. **Today** — due today
3. **Next 7 days** — due tomorrow through today + 7
4. **Later** — due after that
5. **No due date**

Each bucket is ordered by due date, then creation time. Below them, **Recently completed** (collapsed) shows the last 30 tasks the viewer completed. Completing a task from My Tasks is optimistic and it moves to "Recently completed" on refresh (in both layouts; completed tasks are never in sections, and a reopened one returns to its section).

## Workflows model

Migration `20261005020000_workflows.sql`, tests in `supabase/tests/30_workflows_smoke.sql`. Everything is generic: a **request type is a project + its custom fields + a form + rules**. The Autumn Lake patterns (due-tomorrow ping, requester updates, nudges, tracking emails, approval routing) ship only as installable rule templates with placeholder inputs.

### System-written tables and the rule context

- `approval_requests`, `form_submissions`, `rule_runs`, `scheduled_rule_actions`, `rule_presets`, and `email_outbox` are written only by SECURITY DEFINER functions/triggers. Like `task_stories`, they have a `_select_allowlisted` policy and **no insert/update policies**. The outbox is claimed and completed only by `service_role` RPCs.
- `request_sequences`, `forms`, and `rules` follow the full `<table>_{select,insert,update}_allowlisted` pattern with soft delete.
- `public.is_client_role()` (`current_user in ('anon','authenticated')`) lets invoker guard triggers block client writes to system columns while definer code passes. Example: `tasks_10_guard_system_columns` rejects client changes to `tasks.source`, `req_project_id`, `req_number`.
- While a rule runs, transaction-local GUCs `alhc.rule_id` / `alhc.rule_chain` are set. `current_actor_id()` returns null inside a rule, so stories and inbox items show the rule (`data.rule_id`, `data.rule_name`) as the actor and nobody is skipped as "the actor". `comments.author_id` is nullable only for rule comments (`comments.rule_id`, check: author or rule).

### Req # (native request numbering)

- **Choice: dedicated columns, not a custom field.** `tasks.req_project_id` + `tasks.req_number` (unique together) with the label computed by `format_request_label(project, number)` → `prefix || lpad(number, pad_width)`, e.g. `Req #042`. Columns keep the number immutable (clients can't edit it), unique, sortable, and independent of field renames. `task_request_label(task)` returns the label for display.
- `request_sequences` (one row per project): `enabled`, `prefix` (default `Req #`), `pad_width` 0–8, `add_to_title` (prefixes the title with `[Req #042] ` at insert), `assign_to` `all_tasks` | `form_submissions`, `last_number`. Settings tab → "Request numbers"; setting a "next number" continues an existing (e.g. Zapier-era) sequence. `last_number` can never decrease (guard trigger).
- Assignment is atomic: `next_request_number()` is `update request_sequences set last_number = last_number + 1 … returning`, so concurrent creates serialize on the row lock. It runs in the before-insert trigger `tasks_20_assign_request_number` against the **home project's** sequence (subtasks are never numbered, and `assign_request_number` refuses them), so a new task never gets a separate "renamed" story. `rpc("assign_request_number", { target_task })` numbers an older task on demand (task pane button). Multi-homing doesn't renumber: a task keeps the number from the project that issued it.

### Approvals

- `approval_requests (task_id, subtask_id?, approver_id, requested_by, rule_id?, note, status, decided_by, decided_at, decision_note)`. Status: `pending` → `approved` | `changes_requested` | `rejected`, or `cancelled`. `changes_requested` can be **resubmitted** back to `pending`. History is the task's stories (`approval_requested`, `approval_decided`, `approval_resubmitted`, `approval_cancelled`).
- All state changes are RPCs (no client insert/update policy): `request_approval(target_task, approver, approval_note, as_subtask, subtask_title)`, `decide_approval(target_approval, decision, decision_note)` — **approver only, pending only** — `resubmit_approval`, `cancel_approval` (open = pending or changes requested). Since Teams & permissions: requesting, resubmitting, and cancelling need **Editor** on the task; the approver must have at least **Commenter** (checked by `request_approval` and again by `decide_approval`). Rule-created approvals skip the request check, so a rule that names a non-member approver creates an approval nobody can decide.
- By default a request also creates an **approval subtask** (title defaults to "Approval"; since Real subtasks a child task, `approval_requests.subtask_id` → `tasks`). Clients can't tick an approval subtask while its approval is open (`guard_task_kind()`, `check_violation`); `approved`/`rejected` completes it (no extra `completed` inbox items), `changes_requested` leaves it open.
- Notifications: the approver follows the task and gets an `approval_requested` inbox item (again on resubmit). A decision notifies the requester, the assignee, and all followers (`approval_decided`, `inbox_items.data` carries status + note). The decider is never notified of their own action.
- `projects.approval_completes_task` (Settings tab): when on, an `approved` decision also completes the task. Every decision fires `approval_decided` rules.
- **Approval tasks** (`tasks.kind = 'approval'`, Task types and nested rollups) reuse all of this: the assignee is the approver, the request has no approval subtask, and approved / rejected complete the task. See “Task types and nested rollups model”.

### Forms

- `forms (project_id, title, description, questions jsonb, destination_section_id, accepting_responses, send_confirmation, confirmation_message)`. New forms start closed. `questions` is an ordered array validated by `validate_form`:
  `{ id, type: short_text|long_text|number|date|single_select|multi_select|checkbox|email|heading, label, help?, required?, options?: [{id,label}], maps_to?: { target: title|notes|due_on|section|field, field_id? }, show_if?: { question_id, option_ids[] } }` (`email` and `heading` since Asana parity, batch 4: an email answer is lowercased and checked like the submitter's; a heading only shows its label and help, is never answered, required, or mapped, and can't drive branching).
- **Branching:** `show_if` may only reference an *earlier* choice/checkbox question (checkbox option id is `"true"`). Visibility is walked in order; a question whose parent is hidden is hidden too. Hidden answers are dropped server-side. `src/lib/forms.ts` implements the same walk + validation for the browser; `submit_form` re-validates everything (the DB is the trust boundary).
- **Mapping:** `title` (else "<form title> — <email>"), `notes` (else every unmapped answer is summarized in the description), `due_on` (date questions), `section` (single choice; options match a section by id then name), `field` (writes `task_field_values`; select options match by option id then name; a **section-bound Status field maps to the section** instead of a stored value). Destination section otherwise.
- **Submitting:** `rpc("submit_form", { target_form, submitter_email, answers })` is granted to `anon` and `authenticated`. It checks the form is accepting, rate-limits (5/min per email per form), creates the task with `source = 'form'` (there is no "is submission" field — use the `source_is` rule condition or `tasks.source`), applies mappings, assigns a Req # (trigger), records `form_submissions` (email, profile if signed in, cleaned answers), writes a `form_submitted` story, queues the `form_confirmation` email, and fires `form_submitted` rules (plus `task_created` at commit). The Server Action adds a honeypot field and calls `get_public_form` first to validate with the same rules.
- **Public URLs:** `/forms/<id>` (standalone) and `/forms/<id>/embed` (no chrome, for `<iframe>`). Both are public paths in the proxy and read through `get_public_form`, which strips `maps_to` and returns no questions while closed (members of the form's project still see them, for preview). Anonymous submitters never need a membership: `submit_form` is SECURITY DEFINER. The builder shows the link and a ready-made iframe snippet. **Marketing Request Forms hub:** a hub is just a page (Notion, website, intranet, or later an app page) that links or iframes several `/forms/<id>/embed` URLs, one per request type/project. Nothing in the schema knows about a hub; the project chosen per form determines where tasks land.

### Rules engine

- `rules (project_id, name, enabled default false, trigger_type, trigger_config, conditions jsonb[], actions jsonb[], preset_key)`; validated by `validate_rule` (sections/fields/forms must belong to the rule's project). Vocabulary is documented in the migration comment block above `rule_runs` and mirrored in `src/lib/rules.ts`:
  - triggers: `task_created`, `section_changed {section_id}`, `field_changed {field_id, option_id?}`, `assignee_changed`, `due_approaching {days, timezone?}`, `approval_decided {statuses?}`, `form_submitted {form_id?}`, `inbound_received {endpoint_id?}` (since Inbound integrations: a task created through an inbound webhook);
  - conditions (AND): `section_is[_not]`, `field_equals`, `field_is_set`/`_empty`, `assignee_is_set`/`_empty`, `is_complete`/`is_incomplete`, `source_is {source: manual | form | import | inbound}`;
  - actions (in order, max 10): `move_section`, `set_field`, `set_assignee`, `add_comment` (supports `@{assignee}`), `add_followers`, `notify` (inbox kind `rule`), `request_approval`, `send_email {to: submitter|assignee|field|address, template, subject?, message?, include_field_id?}`, `send_slack {message, use_project_webhook?, webhook_ref?, webhook_hint?}`, `call_webhook {use_project_webhook?, url_ref?, url_hint?, secret_ref?, secret_set?, secret_header?}` (see “Integrations model”), `delay {hours}`. People = profile id or role `assignee`/`creator`. Text tokens: `{assignee} {creator} {task} {section} {project} {req} {due} {approval_note}` (`{project}` since Integrations), plus `{task_link}` in Slack messages only (since Integration depth). `send_slack` also takes `format: text | blocks` and `call_webhook` a generated signing secret (`signing_ref` / `signing_set`) — see “Integration depth model”.
- **Firing:** row triggers on `task_projects` (section), `task_field_values` (field), `tasks` (assignee) — **all skip subtasks**, as do `task_created` and `approval_decided` (Real subtasks; `fire_rules` itself is unchanged); `task_created` is a deferred constraint trigger so it sees the fully built task at commit. Changes made in the task's creation transaction don't fire section/field rules (no double-firing on create) unless a rule made them. `fire_rules` only runs **enabled, non-deleted** rules of projects the task is in.
- **Branches (Asana parity, batch 4):** a condition or action may carry `"branch": 0–4` (missing = 0). `run_rule` runs the actions of the first branch whose conditions pass (`rule_pick_branch`: Check if, then each Else if, then Otherwise = a last branch without conditions); a rule without branch keys is one branch and behaves exactly as before. A delayed job re-checks only the branch its remaining actions came from. Limits per branch (`validate_rule_branches`): 1–10 actions, ≤ 20 conditions, up to 5 branches, and only the last branch may have no conditions. `rule_runs.detail.branch` records the branch taken (branched rules only). The stash trigger, the copy engine, and the importer keep the keys like any other.
- **Loop guard:** a rule never re-enters its own chain (`alhc.rule_chain`), chains stop at depth 5, and a rule runs at most 20 times per task per hour. Skips are logged (`rule_runs.status = 'skipped'`, `detail.reason` = `loop` | `depth_limit` | `throttled`). Every run is logged in `rule_runs` (succeeded / failed / skipped / scheduled); the Rules tab shows the latest 50.
- **Section-bound Status:** the Status field has no stored values, so `set_field` on it becomes `move_section`, and `field_changed` can't target it (use `section_changed`). There is one source of truth, so rules can't fight Status.
- **Delays & due dates:** `delay` stores the remaining actions in `scheduled_rule_actions`; `workflow_tick()` (service_role) runs due jobs (re-checking enabled + conditions, else `cancelled`) and evaluates `due_approaching` rules once per task per due date (`rule_runs.dedupe_key = 'due:<date>'`). The migration schedules `alhc-workflow-tick` every 5 minutes **if `pg_cron` is installed**; otherwise `/api/cron/workflows` runs it.
- **Templates:** `rule_presets` rows hold rule JSON with `{"slot": "<key>"}` placeholders and an `inputs` list (section / field / person / text / number). `rpc("install_rule_preset", { target_project, preset, inputs, enable })` fills the slots and inserts ordinary rules (disabled unless `enable`). Seeded: `due_tomorrow_reminder`, `requester_update_on_section`, `stale_section_nudge` (24 h), `tracking_update_email`, `approval_routing` (3 rules), `intake_triage`. No ids, names, or teams are hard-coded. Importing rules from elsewhere must insert them **disabled**.

### Email

- The database never sends mail. `enqueue_email()` writes `email_outbox` (templates `form_confirmation`, `requester_update`, `due_tomorrow`, `custom`) and an `email_queued` story. After every Server Action (`after()`), and on each cron run, `drainOutbox()` claims rows with `claim_email_outbox` (`service_role`, `for update skip locked`), renders them in `src/lib/email.ts`, posts to Resend (`Idempotency-Key: outbox-<id>`), and records the result with `complete_email_outbox` (`sent` / `mocked`; errors go back to `pending` for retry and become `failed` after 5 attempts).
- **Since Email live:** comment emails to followers (template `custom` with `comment_id`), live status on `email_queued` activity lines, Deliveries for emails, per-row `max_attempts` with the integration backoff, and a pg_cron + pg_net kick so nothing waits for the daily cron — see “Email live model”.
- **Mocking:** without `RESEND_API_KEY` + `EMAIL_FROM` rows are marked `mocked` and logged as `[email:mocked] id=… template=…` (never an address, subject, or body). Without `SUPABASE_SERVICE_ROLE_KEY` rows stay `pending` until a configured deployment drains them.
- **Scheduling:** `vercel.json` runs `/api/cron/workflows` daily (the Hobby-plan limit); on Pro, raise the schedule (e.g. `*/15 * * * *`) or point any external scheduler at it with `Authorization: Bearer $CRON_SECRET`.

## Views & Insights model

Migration `20261005030000_views_insights.sql`, tests in `supabase/tests/40_views_insights_smoke.sql`. Views and dashboards are generic project features; nothing knows about a team or request type.

### Saved views (`project_views`)

- `project_views (project_id, name 1–100, layout list|board|calendar|timeline, config jsonb, sort_order, created_by)`, soft delete, full `_{select,insert,update}_allowlisted` RLS. Views are shared by everyone in the project (no private views yet). `project_id` is immutable and `config` is validated on write by `validate_view_config` (trigger `project_views_validate`): unknown keys/values, sections or fields from another project, a non-single-select or section-bound `group_by` field, or more than 3 sorts raise `check_violation`.
- **Defaults:** `projects_create_default_views` (SECURITY DEFINER) gives every new project **List**, **Board**, **Calendar**, and **Timeline** views with an empty config. The views migration backfilled the first three; the timeline migration backfilled one **Timeline** view per project (after its current last tab) wherever none was active. The last remaining view of a project can't be deleted (`deleteView`), so a project always has a tab. `/projects/<id>` redirects to the first view by `sort_order`; `/list`, `/board`, `/calendar`, `/timeline` redirect to the first view with that layout (or render the default config if there is none).
- **Config schema** (documented in full at the top of the migration, mirrored by `src/lib/views.ts`):

  ```
  filters:  completion incomplete|completed|all (default incomplete = "show completed" off)
            completed_within_days N (requires completion = completed)
            sections [uuid | null]     assignees [uuid | "me" | null]   (any-of; null = none)
            due { kind: overdue | today | upcoming (days, default 7) | no_date | range (from, to) }
            fields [{ field_id, op: in | equals | empty | not_empty, values? | value? }]   (all must match)
            text   (title or notes contains, case-insensitive)
            tags [uuid | null]   (any-of; null = no tags; since Tags and collaboration extras)
  sort:     up to 3 × { key: manual | due | start | title | created | assignee | field:<uuid>, dir }   default manual
  group_by: section (default) | assignee | tag | none | field:<uuid> (single-select, not section-bound)
            (tag: a task with several tags shows under each, then “No tag”)
  columns:  [assignee | due | start | section | field:<uuid>]   List columns / Board card fields;
            absent = assignee, due, and every field pinned with show_in_views
  show_subtasks: true | false   List draws each task's subtask tree (absent = off; since Scheduling depth and polish)
  ```

  `show_completed` is not a separate key: the toolbar's "Show completed" checkbox toggles `filters.completion` between `incomplete` and `all`. Field conditions follow the field type: selects/people use `in` (any of the option/profile ids; multi-select and people match on overlap), text/number/date/checkbox use `equals` (text compares case-insensitively), and every type supports `empty` / `not_empty` (`null`, `""`, `[]`, and `false` count as empty). A section-bound Status field compares the task's section in the project.
- **Evaluation:** filtering happens in Postgres. `rpc("filter_project_tasks", { target_project, filters, tz })` (SECURITY INVOKER, so RLS applies) returns the matching active task ids in the project; `data.ts` `filterProjectTaskIds()` calls it and the page keeps only those tasks. Sorting, grouping, and columns are applied in the browser (`components/project/view-groups.ts`) because they don't change membership. `"me"` resolves to `auth.uid()`. The browser parser (`parseViewConfig`) drops invalid parts and `pruneConfig` drops references to deleted sections, fields, and people, so a stale view still renders.
- **Relative dates use the viewer's time zone.** `TimeZoneCookie` (in the app layout) writes the browser's IANA zone to the `tz` cookie and refreshes when it changes; `getViewerTimeZone()` validates it and `safe_timezone()` falls back to UTC. "Overdue" = due before local today and incomplete; "today", "upcoming", and "completed in the last N days" use local days.
- **Unsaved changes live in the URL.** Editing filters, sort, group, columns, or search in the toolbar writes the canonical config to `?f=` (max 8000 chars) without saving. The toolbar then shows "Unsaved changes" with **Reset** and **Save view** (`updateView`); **Save as new view** (`createView`) is in the toolbar's Options menu (since Asana parity, batch 2, where the List's column header menus write the same draft). Filter chips under the toolbar show every active filter and remove it on click. Shared `?f=` links reproduce the same view.
- **Tabs:** the project header starts with **Overview** (since Asana parity, batch 2), lists views by `sort_order`, then fixed tabs (Dashboard, Messages, Workload, Files); Fields, Forms, Rules, and Settings open from the Customize panel (since Asana feel, batch 1). The "+" at the end creates a list/board/calendar/timeline view; each tab's menu has Rename, Duplicate ("<name> copy"), Move left/right, and Delete (soft).
- **List / Board with views:** groups come from `group_by`. Section groups show "No section" plus every section (only the filtered ones when a section filter is set), assignee groups end with "Unassigned", field groups end with "No <field>". Drag-and-drop on Board changes what the column represents: section → `placeTask` (manual order) or `moveTask` (append), assignee → `updateTask({ assigneeId })`, field option → `setFieldValue`. A precise drop position (fractional `sort_order`) is only used with manual sort and section grouping; otherwise the card is appended. List rows drag only in that mode (within and across sections, via `place_task`), and List sections drag (or use ↑/↓ buttons) via `place_section` whenever the view is grouped by section without a section filter (see “Bulk edit and shortcuts model”). Adding tasks inline is offered only in section groups.
- **Subtasks are not view rows** (List, Board, Calendar, or Timeline): they have no project membership, so `filter_project_tasks`, sorting, grouping, and Board columns only ever see top-level tasks. List's toolbar has **Show subtasks** (the view config's `show_subtasks`, off by default; toggling it is an unsaved `?f=` change saved with **Save view**, and an old `?sub=1` link opens as that draft), which draws each listed task's subtask tree under its row (indented, completable, opens the pane; not selectable, draggable, or filtered). Rows and cards show `x/y` done for direct subtasks.

### Calendar

- Month view (weeks start Sunday) and week view; the period is in the URL (`?d=YYYY-MM-DD`, `?cal=week`), with Today and previous/next controls. Tasks are placed by **`tasks.due_on`** only (there is no due time; `start_on` is ignored here — Timeline is the view that uses it). Dragging a task to a day before its start date is rejected with the start-after-due error. Completed tasks that pass the view's filters are shown struck through; overdue incomplete tasks get a red dot; milestones get a diamond instead of the dot.
- The view's filters apply to the grid. The right-hand **No due date** tray lists the filtered tasks that have no due date and are incomplete.
- Clicking a task opens the normal task pane (`?task=`). Dragging a task to a day sets its due date (optimistic, logged as `due_changed`; a later date goes through auto-shift, see “Scheduling depth and polish model”); dropping it on the tray clears the due date. Month cells show three tasks, then "+N more" expands the day.

### Timeline

Migration `20261005040000_timeline.sql`, tests in `supabase/tests/50_timeline_smoke.sql`. A Gantt-style layout built with plain CSS-positioned bars (no chart library).

- **Bars:** `start_on` → `due_on` (inclusive) when both are set. **Due only** = a one-day bar on the due day (not a milestone glyph, so it can be dragged and resized like any bar). **Start only** = a one-day bar on the start day drawn open-ended (dashed outline, “Starts <date>”). Neither = the **Unscheduled** tray. These rules live in `components/project/timeline-scale.ts` (`spanOf`). **Milestones** (`kind = 'milestone'`) are a diamond on the due day instead of a bar: dragging moves it, there are no ends to resize.
- **Colour = status:** accent fill for open tasks, red for overdue (due before the viewer's local today, incomplete), zinc + struck-through title for completed tasks (shown only when the view shows completed tasks), dashed accent outline for start-only tasks. No per-section colours.
- **Scale:** Week (36 px/day, 6 weeks from the Sunday before the anchor's week, weekends shaded), Month (12 px/day, 4 months from the anchor's month), Quarter (4 px/day, 4 quarters). The zoom and anchor are URL state like Calendar (`?tl=month|quarter`, default week; `?d=YYYY-MM-DD`) with Today and earlier/later controls; they are not saved in the view config. A vertical accent line marks today. A task outside the window shows a “‹ Sep 12” / “Dec 3 ›” button on its row that jumps the window to it.
- **Rows:** one per scheduled task (start or due set) passing the view's filters, grouped and ordered by the view's `group_by` and `sort` exactly like List (`groupTasks`); empty groups are hidden. The toolbar offers Filter, Sort, Group, and Show completed (no Columns). The sticky left column lists task names as links — the keyboard and screen-reader path to the pane — with the dates, overdue/completed state, and assignee spelled out for screen readers; the bars themselves are pointer-only (`aria-hidden`).
- **Critical path (Critical path and portfolio depth):** the toolbar's **Critical path** button (`?cp=1`, URL state like the zoom) outlines critical bars, fades the rest, and draws arrows between critical tasks darker; a note says how many tasks have no due date and were skipped. Bar tooltips and the name link's screen-reader text carry the slack (`slackLabel()`), and the pane's Dependencies section lists it per project. Numbers come from `project_critical_path()` over every readable task of the project (not just the view's filtered tasks), loaded only for the timeline layout. Read-only: nothing is shifted. See “Critical path and portfolio depth model”.
- **Dependency arrows (Task depth):** an SVG overlay draws an arrow from each predecessor bar's end (finish-to-start) or start (start-to-start, since Scheduling depth and polish) to its successor bar's start when both rows are shown and both bars are at least partly inside the window (`listProjectDependencies()` → `rpc("project_dependencies")`: links between two active tasks of the project, wherever they were made; loaded only for the timeline layout). Arrows are red when the successor starts before the link allows (`dependencyConflict()` in `src/lib/dependencies.ts`: predecessor's due, or start, + lag). They are pointer-transparent and `aria-hidden`; the name link's screen-reader text says "blocked by N", and the pane lists the dependencies. Row positions are computed from fixed row heights (`HEADER_HEIGHT` / `GROUP_HEIGHT` / `ROW_HEIGHT` in `timeline-view.tsx`), so keep them in sync with the row classes.
- **Interactions:** clicking a bar or a name opens the task pane (`?task=`). Dragging a bar **moves** it (whichever dates are set shift by the same number of days); dragging either **end** resizes it (that edge is set and the other kept, so a single-date task gains both dates; edges never cross). Both commit the new dates optimistically and log `start_changed` / `due_changed`; since Scheduling depth and polish they go through `useDependencyShift()` (a later date that breaks a dependent's start asks before moving it, with Undo). Dragging a task from the Unscheduled tray onto a day sets its **due date** only. Clearing dates happens in the pane.
- **Unscheduled tray:** incomplete filtered tasks with neither date (due-only and start-only tasks are bars, not tray items).
- **Start dates elsewhere:** the pane has a Start date input next to Due date (each limits the other with `min`/`max`, and a rejected change resets the input). List can show a **Start** column and Board cards a start chip via the `start` column key; views can sort by `start`.

### Dashboard (`dashboard_widgets`)

- `dashboard_widgets (project_id, kind count|by_section|by_assignee, title, filters, sort_order, created_by)`, soft delete, full allowlisted RLS. `filters` uses the same filter schema as views and is validated by `validate_view_filters` (trigger `dashboard_widgets_validate`).
- Metrics come from `rpc("project_metrics", { target_project, filters, group_by: none|section|assignee, tz })` (SECURITY INVOKER over `filter_project_tasks`, so counts never include rows the caller can't read): one row per bucket with `task_count`; a `null` bucket is "No section" / "Unassigned".
- Widgets: **number card** (`count`), **bar chart by section** (`by_section`, project section order, "No section" only if non-zero), **bar chart by assignee** (`by_assignee`, largest first, Unassigned last). Charts use Recharts (MIT) with an `sr-only` table for screen readers. Each widget shows its filters as chips and a "View tasks" link that opens the List view with the same filters as a `?f=` draft.
- Widgets can be added (blank or "Add starter widgets": Incomplete tasks, Overdue, Completed in the last 7 days, Incomplete by section, Incomplete by assignee), edited (title, kind, filters), moved earlier/later, and removed (soft).

## Teams & permissions model

Migration `20261005050000_teams_permissions.sql`, tests in `supabase/tests/60_teams_permissions_smoke.sql`. Still generic: membership is per project, with no team or department baked in.

### Membership (`project_members`)

- `project_members (id, project_id, profile_id, role, created_by, created_at, updated_at, deleted_at)`; role ∈ `owner | admin | editor | commenter | viewer`. One **active** row per (project, person) (partial unique index where `deleted_at is null`). Removal is a soft delete and is kept as history; re-inviting creates a new row. A soft-deleted membership grants nothing.
- Writes only through SECURITY DEFINER RPCs (no insert/update policy): `add_project_member(target_project, member_email, member_role)` (invite by email; re-inviting an active member changes their role), `update_project_member_role(target_project, target_profile, new_role)`, `remove_project_member(target_project, target_profile)` (anyone may remove themselves = leave), `transfer_project_ownership(target_project, target_profile)` (target becomes owner, caller steps down to admin). Members of a project can read its member list (`project_members_select_viewer`).
- **Invites:** the address must already be on `allowed_emails` **and** its owner must have signed in once with a confirmed email (so a `profiles` row exists); since Asana feel, batch 2, an allowlisted address without a confirmed account gets a pending invite instead (the RPC returns null; see “Asana feel model (batch 2)”), and an address not in the workspace still raises with a hint. Invites do not create an inbox item (inbox items are task-scoped).
- **Guests** are not a separate account type: a guest is an allowlisted person invited to a project with a lower role (usually Viewer or Commenter). The Members page says so in its copy.
- **Invariants:** a project always keeps an active owner (`project_members_guard` rejects demoting or removing the last one, locking the project row so concurrent changes serialise); memberships can't move between projects/people; only owners can add, change, or remove owners; admins grant up to admin.
- **New projects:** `projects_add_owner` (AFTER INSERT, SECURITY DEFINER) makes the creator the owner. `projects_05_guard_columns` forces `created_by = auth.uid()` and `created_at = now()` on client inserts and makes them immutable, and rejects soft-deleting/restoring a project unless the caller is an owner. Because the owner row is written after `INSERT … RETURNING` is checked, `projects_select_viewer` also lets the creator read the row in its creating transaction (`created_by = auth.uid() and created_at = now()`); that can't be replayed later.
- **Backfill** (`backfill_project_members()`, idempotent, not an RPC; run once by the migration): every project without an owner gets its creator as owner, or — when `created_by` is null — the oldest allowlisted profile; then every other currently allowlisted (confirmed) profile joins every project as **Editor**, so the single team using the app keeps working. Owners/admins narrow access per project afterwards.

### Roles and helpers

Total order `viewer < commenter < editor < admin < owner` (`project_role_rank()`; `src/lib/roles.ts` mirrors it). Helpers (SECURITY DEFINER, `search_path = ''`, all require `is_allowlisted()`): `project_role(project)`, `has_project_role(project, min_role)`, `task_role(task)`, `has_task_role(task, min_role)`, `profile_can_read_task(profile, task)` (only answers for tasks the caller can read). **A task's role is the caller's highest role across the task's active project memberships plus its home project** (for a subtask: its root task's) — so a task multi-homed into a project you edit is editable by you, while its other projects stay invisible (`task_projects` rows are visible per project). Internal helpers (`profile_project_role`, `profile_task_role`, `profile_is_allowlisted`) are revoked from clients.

## Task depth model

Migration `20261005060000_task_depth.sql`, tests in `supabase/tests/70_task_depth_smoke.sql`. Generic: nothing knows about a team or request type.

### Recurring tasks

- **Rule on the task:** `tasks.recurrence jsonb` (null = one-off), validated and normalized by `normalize_recurrence()` (trigger `tasks_16_validate_recurrence`) and mirrored by `src/lib/recurrence.ts`:
  `{ freq: daily|weekly|monthly|yearly, interval: 1–365, weekdays?: [0–6] (weekly only, 0 = Sunday), ends: {type: never} | {type: after, count: 1–1000} | {type: until, until: YYYY-MM-DD}, timezone: IANA (default UTC), month_day?: 1–31 (system) }`. Unknown keys and values raise `check_violation`. Editors set it through `updateTask`-style RLS (`setTaskRecurrence`); viewers' updates affect zero rows. A `recurrence_changed` story logs each change.
- **Spawn on complete (Asana style, not roll-forward):** `tasks_after_complete_recur` (SECURITY DEFINER `spawn_next_occurrence()`) fires when a task with a rule goes incomplete → complete, by anyone (person, rule, approval). It inserts **one** new incomplete task: same title (a `[Req #…] ` prefix is stripped so the new task gets its own number), kind, notes, assignee, creator, home project, other projects + sections (end of each section), stored custom field values (values that no longer validate are skipped), followers, and the full subtask tree (every active non-approval subtask, open, with its assignee, notes, kind, field values, followers, and dates shifted by the same days — `copy_subtask_tree()`); not comments, attachments, approvals, or dependencies. A recurring subtask spawns under the same parent (nothing spawns once the parent is gone). Dates shift by the same number of days from the **anchor** (due date, else start date, else the completion day in the rule's zone) to `recurrence_next_date(rule, anchor)`; times keep their local time of day in `tasks.time_zone`; an undated task's next occurrence is due on the next date. The new task's `recurrence_seq` is +1 and `recurrence_series_id` is the first task's id; the completed task gets `recurrence_next_id` and a `recurrence_spawned` story (with a link in the pane). The new task fires `task_created` rules at commit like any new task.
- **Rules of the series:** reopening and completing again does not spawn a second copy while the spawned one is active (deleting the spawned occurrence lets the next completion spawn again). `ends.after N` stops once occurrence N is completed; `ends.until` stops when the next anchor would be after that date. Monthly/yearly remember the anchor's day (`month_day`) so Jan 31 → Feb 28 → Mar 31; Feb 29 yearly lands on Feb 28 in common years. Weekly with weekdays picks the next listed weekday in a week that is a multiple of `interval` weeks from the anchor's week (weeks start Sunday). Clients can't write `recurrence_series_id` / `recurrence_seq` / `recurrence_next_id` (`tasks_11_guard_recurrence_columns`).
- **UI:** **Repeats** (at the bottom of the due date picker since Asana parity, batch 3; frequency, every N, weekday toggles, ends never/after/on date, summary like “Every 2 weeks on Mon, Wed · until Dec 31, 2026”); a repeat icon on List rows and Board cards (`ProjectTask.recurring`).

### Due and start times

- `tasks.due_at` / `start_at` (timestamptz, optional) + `tasks.time_zone` (IANA, normalized by `safe_timezone()`). `tasks_15_sync_times` keeps `due_on`/`start_on` equal to the local date of the time: setting a time sets its date; changing only the date (Calendar/Timeline drag) moves the time to the new date at the same local time; clearing a date clears its time; clearing a time keeps the date. Constraints: `tasks_start_at_before_due_at`, `tasks_due_at_has_date`, `tasks_start_at_has_date`, plus the existing date constraint.
- The pane sends the browser's zone with every time it sets (`updateTask({ dueAt, timeZone })`); times are shown in the viewer's local zone (client-only render). Calendar, Timeline, List, Board, My Tasks, filters, rules, and forms stay day-based.

### Dependencies

- `task_dependencies (id, project_id, predecessor_id, successor_id, kind 'finish_to_start', created_by, created_at, updated_at, deleted_at)`; one **active** row per (predecessor, successor) (partial unique index); `predecessor_id <> successor_id`. Soft delete keeps history; re-adding creates a new row. **Since Scheduling depth and polish** links also have `start_to_start` kind and `lag_days`, may join subtasks and tasks of different projects, are read with access to both tasks, and are written by `set_task_dependency` (Editor on both); `project_id` is informational. See “Scheduling depth and polish model” — the bullets below describe the Task depth original, still true of `add_task_dependency`.
- **Writes only via SECURITY DEFINER RPCs** (no insert/update policy): `add_task_dependency(predecessor, successor)` (both tasks active and readable; they must share an active project where the caller is **Editor**, else `check_violation` “same project” / `insufficient_privilege`; idempotent for an existing pair; rejects cycles with a recursive walk under a transaction advisory lock) and `remove_task_dependency(target_dependency)` (Editor in the dependency's project). Both write `dependency_added` / `dependency_removed` stories on both tasks. Read: `task_dependencies_select_viewer` (viewer of `project_id`).
- **Blocking, not warning:** `tasks_12_guard_dependencies` (runs as the caller) rejects a person completing a task while any active, non-deleted predecessor is incomplete (`check_violation`, “This task is blocked by N incomplete tasks”, with a hint). System completions (rules, `approval_completes_task`) are not blocked. `open_blocker_count(task)` (returns 0 for tasks the caller can't read) backs the guard. Reopening a predecessor does not reopen its successors.
- **UI:** pane section **Dependencies** with **Blocked by** and **Blocking** lists (links, completion state, remove), and pickers of tasks from the task's projects where the viewer is an Editor (`TaskDetail.dependencyCandidates`, 300 per project). **Mark complete** is disabled with “Blocked by N tasks” while blocked. List/Board show a lock + count (`ProjectTask.blockedBy`). Timeline draws arrows (see Timeline).

### Trash

- A deleted task stays a row with `deleted_at`. `tasks_select_viewer` now shows **active** tasks to viewers+ and **trashed** tasks only to Editors+ (home project or any active membership), so Viewers/Commenters and non-members never read trashed titles. Views (`filter_project_tasks`), search (`search_tasks`), My Tasks, Inbox, rules, and the dashboard all filter `deleted_at` as before.
- `restore_task(target_task)` (SECURITY DEFINER, Editor on the task) clears `deleted_at` (refuses when the home project is deleted); `tasks_after_restore` writes a `restored` story. The plain RLS update path would also work for editors; the RPC gives a clear error and is what the app calls.
- **Trash page:** Settings → **Trash** (`/projects/<id>/settings/trash`) lists up to 200 trashed tasks with an active membership in the project (newest first, who deleted it from the `deleted` story, home project when different), with a confirmed **Restore**. Below Editor the page shows a notice instead of a list. There is no permanent delete.

## Portfolios and reporting model

Migration `20261005070000_portfolios.sql`, tests in `supabase/tests/80_portfolios_smoke.sql`. A **portfolio** is a named collection of projects with a progress overview and simple cross-project reporting. Generic: nothing knows about a team or request type.

### Tables

- `portfolios (id, workspace_id, name 1–100 chars, notes, created_by, created_at, updated_at, deleted_at)`. - `portfolio_members (id, portfolio_id, profile_id, role owner|admin|editor|viewer, created_by, …, deleted_at)`: one active row per (portfolio, person); removal is a soft delete kept as history; re-inviting creates a new row. `portfolio_members_guard` keeps memberships from moving and enforces the **last-owner invariant** (locks the portfolio row).
- `portfolio_projects (id, portfolio_id, project_id, sort_order double precision, created_by, …, deleted_at)`: one active row per pair (partial unique index); removing soft-deletes, re-adding creates a new row. `portfolio_projects_guard` keeps rows from moving.
- **Project status** on `projects`: `status` (`on_track` | `at_risk` | `off_track` | `complete`, default `on_track`), `status_note` (≤ 2000 chars), `status_updated_at`, `status_updated_by`. Written only by `rpc("set_project_status", { target_project, new_status, note })` (**Editor+** on the project; stamps who/when); `projects_06_guard_status` rejects client writes to these columns (including admins' direct project updates). Shown as a badge on portfolio cards and the report; set in project Settings → General. Since Critical path and portfolio depth every call also appends a `project_status_updates` row (history feed under the form; latest update on portfolio cards and as a Report column).

### Progress and reporting

- **Progress formula:** over every active task with an active `task_projects` membership in at least one active project of the portfolio that the viewer can read (`has_project_role(project, 'viewer')`), **percent = floor(100 × completed / (completed + incomplete))**, each task counted **once** (deduped by `tasks.id`) even when multi-homed into several of the portfolio's projects. Soft-deleted tasks, projects, task memberships, and `portfolio_projects` rows are excluded. **Denominator 0 ⇒ no percentage; the UI shows "No tasks"** (`progressPercent()` returns null). Rounded down so 100% only ever means everything is done.
- **Overdue** = incomplete with `due_on` before the viewer's local today (`tz` cookie, as in views and the dashboard). **Completed recently** = completed on one of the viewer's last **7** local days, today included (same as the views filter `completed_within_days = 7`; `RECENT_DAYS` in `src/lib/portfolios.ts`).
- `rpc("portfolio_report", { target_portfolio, group_by: none|project|assignee, tz })` (SECURITY INVOKER, so RLS applies, plus an explicit `has_project_role(..., 'viewer')` per project) returns `bucket, task_count, completed_count, incomplete_count, overdue_count, completed_recent_count`. `none` always returns exactly one row (the deduped portfolio total); `project` returns one row per visible project with tasks (a multi-homed task counts in **each** of its projects); `assignee` is deduped by task (`null` = Unassigned). Non-members get zeros. `rpc("list_portfolio_progress")` (invoker) returns `task_count` / `completed_count` for every readable portfolio in one call, for the sidebar.

## Integrations model

Migration `20261005080000_integrations.sql`, tests in `supabase/tests/90_integrations_smoke.sql`. Two rule actions — **Send Slack message** (`send_slack`, Slack incoming webhook) and **Call webhook** (`call_webhook`, outbound HTTPS JSON) — built on the Workflows email pattern: the rule runner only **queues** a row in `integration_outbox`; the app claims and POSTs it with the service role. **The database never makes HTTP calls.** Generic: nothing knows about a team, channel, or receiver.

### Tables (all secret: RLS on, no policies, no anon/authenticated table grants)

- `integration_outbox (id, channel slack|webhook, project_id, task_id?, rule_id?, rule_run_id?, target_url, target_hint, headers jsonb, payload jsonb, status pending|sending|sent|mocked|failed, attempts, last_error, provider_response jsonb?, send_after, sent_at, created_at, updated_at, deleted_at)`. One generic table with a channel discriminator, mirroring `email_outbox`. `target_url` must pass `integration_url_ok()` (CHECK). `headers` holds the optional shared-secret header for webhooks (`{}` for Slack). `rule_run_id` points at the `rule_runs` row of the run that queued it (FK deferred: `run_rule` now picks the run id up front and exposes it as the transaction-local GUC `alhc.rule_run_id`). **Choice: no client SELECT at all** (not even Admin+), because rows carry the URL and secret; members see the redacted `integration_queued` / `integration_failed` stories instead, and operators read the table with the service role.
- `project_integrations (project_id pk, slack_webhook_url, webhook_url, webhook_secret_header, webhook_secret, updated_by, …, deleted_at)`: per-project defaults. Read only through `rpc("get_project_integrations", { target_project })` (**Admin+**, returns `{ slack_webhook, webhook, webhook_secret_set, webhook_secret_header, updated_at }` with URLs as hints — never a URL or secret) and written only through `rpc("set_project_integration", { target_project, setting, new_value })` (**Admin+**; `setting` ∈ `slack_webhook_url | webhook_url | webhook_secret | webhook_secret_header`; empty/null clears; returns the redacted settings). UI: Settings → **Integrations**.
- `integration_secrets (id, project_id, rule_id, kind slack_url|webhook_url|webhook_secret, value, created_at, deleted_at)`: URLs and secrets typed into a rule action. `rules` stay readable by project Viewers (unchanged), so secrets can't live in `rules.actions`: the BEFORE trigger `rules_05_stash_integration_secrets` (SECURITY DEFINER, runs before `rules_validate`) replaces plain `webhook_url` / `url` / `secret` keys with `webhook_ref` + `webhook_hint`, `url_ref` + `url_hint`, `secret_ref` + `secret_set: true`. A plain `""` clears the value. A ref must belong to the rule's project (else `check_violation`); a ref copied from another rule of the project is cloned; hints are always recomputed (clients can't forge them). Values a rule no longer references are soft-deleted unless a pending delayed job (`scheduled_rule_actions`) still references them.

### Rule actions

- `send_slack { message (1–4000), use_project_webhook?: boolean }` + stored `webhook_ref` / `webhook_hint`. The message supports the usual text tokens plus `{project}`; **substituted values are Slack-escaped** (`&`, `<`, `>`) so a task title can't `<!channel>`, while the admin's own template text is kept as written (Slack link syntax works). Payload = `{ "text": "<rendered message>" }` (plain text), or since Integration depth `{ text, blocks }` with `format: "blocks"` (see “Integration depth model”). A message that renders empty logs outcome `empty` and queues nothing.
- `call_webhook { use_project_webhook?: boolean, secret_header?: string }` + stored `url_ref` / `url_hint`, `secret_ref` / `secret_set`. **Shared secret: sent as a request header** — `X-ALHC-Webhook-Secret: <secret>` by default, or the named header (letters/digits/dashes; `Content-Type`, `Content-Length`, `Host`, `User-Agent`, `Idempotency-Key`, `Transfer-Encoding`, `Connection`, `Accept-Encoding` are reserved — use `Authorization` with a `Bearer …` secret for token auth). Never put in the body. Since Integration depth requests can also be HMAC-signed (`X-ALHC-Signature`, see “Integration depth model”).
- **URL resolution** (at enqueue, in `enqueue_integration()`): `use_project_webhook = true` ⇒ the project default; otherwise the action's own URL, falling back to the project default. An action with its own URL only sends **its own** secret; the project secret is only ever sent to the project URL. **No URL anywhere ⇒ the action raises**, so the run is `failed` with `detail.actions.error` = “Send Slack message: no Slack webhook URL is set on this action or in Settings → Integrations” (or the Call webhook equivalent), the run's earlier actions roll back, and no outbox row is written. The Rules tab's run log shows that message (`runReason()` now also reads `detail.actions.error`).
- **HTTPS only.** `integration_url_ok()` (mirrored by `isAllowedWebhookUrl()` in `src/lib/integrations-shared.ts`) accepts `https://host[:port][/path?query#frag]` with a plain host and rejects `http:`, other schemes, relative URLs, `user:pass@`, whitespace, `localhost` / `*.local` / `*.internal`, and private/loopback/link-local IPv4 literals (including integer, hex, and zero-padded spellings); host names that merely resolve to a private address are not checked. It is checked by the Server Action, the stash trigger / settings RPC, the outbox CHECK constraint, and again by the drain before every POST.
- `validate_rule` accepts both actions (message required for Slack, boolean `use_project_webhook`, valid `secret_header`) and rejects plain URL/secret keys if they ever reach it. The executor (`execute_rule_actions`) calls `enqueue_integration(rule, task, action, event)` and logs outcome `queued` — never a URL.

```json
{
  "event": "section_changed",
  "rule_id": "uuid",
  "rule_name": "Tell the team",
  "project": { "id": "uuid", "name": "Marketing requests" },
  "task": {
    "id": "uuid",
    "title": "Spring flyer",
    "req": "Req #042",
    "section_id": "uuid",
    "section_name": "In progress",
    "assignee_id": "uuid",
    "completed": false,
    "due_on": "2026-11-02",
    "url": "https://<app origin>/projects/<project id>?task=<task id>"
  },

```

`event` = the rule's `trigger_type`; `req`, `section_id`, `section_name`, `assignee_id`, `due_on` may be `null`; `occurred_at` is the enqueue time in UTC. The database stores everything except `task.url`, which the drain adds from `NEXT_PUBLIC_APP_URL` (else `https://$VERCEL_PROJECT_PRODUCTION_URL`) and omits when neither is set. No custom-field dumps, notes, comments, or emails.

### Delivery (`src/lib/integrations.ts`)

- `drainIntegrationOutbox({ max, onlyId })` mirrors `drainOutbox()`: `claim_integration_outbox(max_items, only_id)` (`service_role`, `for update skip locked`, attempts < the row's `max_attempts` (5; since Integration depth), stale `sending` rows reclaimed after 10 min) → POST → `complete_integration_outbox(target_item, outcome, response, error_message)` (`service_role`): `sent` / `mocked`; anything else returns the row to `pending` — since Integration depth after `integration_retry_delay(attempts)` = 5, 10, 20, then 30 minutes (capped; it was a flat 5) — until `max_attempts`, then `failed` plus a redacted `integration_failed` story. `provider_response` keeps `{status, body (≤ 500 chars)}`.
- Requests: `POST`, `Content-Type: application/json`, `User-Agent: ALHC-Projects-Webhook/1.0`, body = stored payload (webhooks add `task.url`); webhooks also send `Idempotency-Key: integration-outbox-<id>` and the stored secret header. 10-second timeout, rows in a batch are sent concurrently, **redirects are not followed** (the secret must only reach the configured host), 2xx = success.
- Without `SUPABASE_SERVICE_ROLE_KEY` nothing is claimed and rows stay `pending`. `INTEGRATIONS_MOCK=true` marks rows `mocked` and logs `[integration:mocked] channel=… target=<hint>` instead of POSTing.
- Triggered from the same places as email: `/api/cron/workflows` (after `workflow_tick` and the email drain; the JSON response includes `integrations` counts) and the Server Action `after()` hook (a batch of 10, so rule fires feel immediate between cron runs).

### Redaction rules

- The only form of a webhook URL that leaves the secret tables is the hint `integration_url_hint(url)` = `<host> …<last 4 chars>` (e.g. `hooks.slack.com …x7Yz`); secrets are only ever “saved” / `secret_set: true`.
- `integration_queued` stories carry `{outbox_id, channel, target: <hint>}` + the rule id/name; `integration_failed` adds `attempts`. `rule_runs.detail` only has action outcomes. `scheduled_rule_actions.actions` holds refs + hints. Drain errors stored in `last_error` use the hint, and network exceptions keep only the error kind (their messages can include the URL). Server Action errors never echo values.
- The rule builder shows saved values as a hint with **Replace** / **Remove** and uses password-style inputs; Settings → Integrations does the same with **Set / Replace / Clear**.

### EXECUTE surface

`get_project_integrations` and `set_project_integration` are the only new client RPCs (pinned in `60_teams_permissions_smoke.sql`). `enqueue_integration`, `stash_rule_integration_secrets`, `render_rule_text_as`, `slack_escape`, `integration_url_ok` / `_hint` / `_host` are revoked from `public`, `anon`, and `authenticated`; `integration_header_ok` (no definer, used by `validate_rule`) is executable by `authenticated` only; `claim_integration_outbox` / `complete_integration_outbox` are `service_role` only. `anon` gains nothing.

## Asana import model

Migration `20261005090000_asana_import.sql`, tests in `supabase/tests/91_asana_import_smoke.sql`. An Admin uploads Asana project exports; the app parses them server-side and writes them into the existing tables. **Never the Asana API, no Asana OAuth, no Asana tokens stored.** Generic underneath: the batch format and the gid map carry a `source` (only `asana` today), and nothing knows about a team or request type.

### Flow

1. **Upload** (browser → Storage): Settings → **Import** (`/projects/<id>/settings/import`, Admin+) uploads `.json` / `.csv` files (≤ 10 files, ≤ 50 MB each) to the private bucket **`imports`** at `<project id>/<uploader id>/<uuid>-<name>`. Policies `imports_objects_{insert,select,delete}_own_admin`: own folder only, and only while Admin+ of the project (`import_object_project(name)` parses the prefix). Upload goes through Storage rather than the Server Action body because Vercel caps request bodies at 4.5 MB.
2. **Dry run** (`previewAsanaImport`): downloads the files with the user's client, `buildImportPlan()` (`src/lib/asana-import.ts`), then reports counts per kind, how many external ids already exist in this project (`rpc("import_lookup")`, SECURITY INVOKER over admin-only RLS), other projects the same Asana project was imported into, sections/fields reused by name, people bucketed as matched member / has an account but not a member / no account / no email, and parser warnings. Writes nothing.
3. **Import** (`runAsanaImport`): optionally invites the "has an account" people as Editors (`add_project_member`), `start_import_run`, then sends batches to `import_batch` for up to ~20 s per call (page `maxDuration = 60`) and returns `{ runId, step, steps, totals }`; the page calls again until done, then `finish_import_run` and the uploaded files are removed. Batches are deterministic for the same files (structure → ≤ 100 tasks / ~1 MB per batch → dependencies in chunks of 1,000), so **Try again** resumes at the failed step. Abandoned uploads are removed on "Start over" or a failed preview.

### Parser (what maps where)

- **JSON export** (`{ "data": [task…] }`, API-shaped tasks with nested `subtasks`): source project = the membership project most tasks share (recorded as kind `project`); sections from that project's memberships (key = section gid); other memberships become `projects: [{gid, section_name}]` for multi-homing; `custom_fields` by gid (`text` → text, `number`/percent/currency → number, `enum` → single_select, `multi_enum` → multi_select, `date` → date, `people` → people, formula / custom ID / anything else → text from `display_value`; enum options from `enum_options` + seen values); `tags` → native workspace tags by name (batch task key `tags`, `import_task_tags()`; before Tags and collaboration extras they went to a **Tags** multi-select field under key `asana:tags`, migrated once — see “Tags and collaboration model”); `followers`; `stories` of type `comment` → comments (system stories are ignored); `attachments` → `permanent_url` / `view_url` only (signed `download_url`s expire); `dependencies` / `dependents` → finish-to-start pairs; `resource_subtype` `milestone` / `approval` → `tasks.kind` (anything else is a task; the CSV has no type column). Top-level rows whose `parent` is another row become its subtasks.
- **CSV export**: `Task ID` (= gid, so CSV and JSON of the same project dedupe against each other), `Name`, `Section/Column`, `Assignee`, `Assignee Email`, `Start Date`, `Due Date` (YYYY-MM-DD or M/D/YYYY), `Completed At`, `Tags`, `Notes`, `Parent task` (id or name → subtask), `Blocked By` / `Blocking (Dependencies)` (ids or names). Every other column is a custom field: same-named JSON field if one exists, else the type is inferred (all numeric → number, all dates → date, ≤ 20 repeating values → single_select, else text). Section/field keys without a gid are `name:<lower name>`.
- **Both together:** JSON wins for tasks in both; the CSV contributes assignee emails (by task → assignee gid, and by name), dependencies, missing subtasks, and CSV-only rows. Asana's JSON export often omits emails, so the preview suggests adding the CSV.
- **Subtasks** (since Real subtasks) are real subtasks: title, completion, notes, due/start dates, kind, and assignee (matched by email like tasks, else noted), nested as in Asana up to 4 levels (`import_subtasks()`); deeper levels are flattened into the 4th and counted in the warnings. JSON rows whose `parent` is another row join that row's subtasks at any level. Re-importing adds only new subtasks, also under ones imported earlier.
- **Rules:** Asana's exports contain none. A JSON file may carry ALHC rule JSON under a top-level `rules` key; those pass through and always land disabled.

### Database

- `import_runs (project_id, source 'asana', status running|completed|failed, file_names, summary, created_by, …, finished_at, deleted_at)`; `summary.created` is counted from the gid map at finish. `import_external_ids (project_id, source, kind project|section|field|task|subtask|comment|attachment|dependency|rule, external_id, local_id, run_id)`, unique per (project, source, kind, external_id), append-only (sections/fields are re-pointed when their row was deleted). `task_attachment_links (task_id, source, name, url https-only or null, deleted_at)`. RLS: `import_runs_select_admin_or_workspace_admin` (Admin+, or a workspace admin who can read the project — one policy since Review hardening), `import_external_ids_select_admin`, `task_attachment_links_select_viewer`; no insert/update policies and client write grants revoked.
- `import_batch(target_run, batch)` (SECURITY DEFINER, Admin+ on the run's project, run still `running`, per-project advisory lock) — batch format documented above the function. **Idempotent:** anything whose external id is already mapped is skipped and never changed (a task deleted here since is left alone); for tasks imported earlier only new subtasks, comments, and attachment links are added. Sections match by key, then by name; fields by key, then by name + type (a same-named field of another type, or the section-bound Status, gets an “ (Asana)” suffix); select options match by name and missing ones are appended. Tasks: `source = 'import'`, `kind` from the batch (`milestone` | `approval`, else `task`), `created_by` = importer, `created_at` = now (Asana's creation time is not kept), completion time and comment times are kept, a start date after the due date is dropped. **People only ever match active project members by email** (`import_member()`): assignee, followers, people-field values, comment authors. An unmatched assignee leaves the task unassigned and appends “— Imported from Asana — / Assignee in Asana: Name <email> (…)” to the notes; an unmatched comment author's comment is posted by the importer as “<name> wrote in Asana:”. Multi-homing only into projects where that Asana project gid was imported before and the importer is Editor+. Dependencies need both tasks active in this project; cycles are skipped. The importer is unfollowed from imported tasks unless they're the assignee or an Asana follower.
- **Muted side effects** while `alhc.import_run_id` is set (transaction-local, left set until commit so the deferred `task_created` trigger sees it; `import_context_id()`): `fire_rules` returns early (no rule runs, emails, Slack, or webhooks), `notify_with` returns early (no inbox items), `add_story` writes only `created` with `data.import = {source, run_id}` (the pane says “imported this task from Asana”), and `rules_03_import_disabled` forces `enabled = false` on any rule inserted. Req # sequences still number imported tasks like any new task.
- `finish_import_run(target_run, run_status, run_summary)` and `start_import_run(target_project, import_source, file_names)` are Admin+. EXECUTE: the three are the only new client RPCs (pinned in `60_teams_permissions_smoke.sql`); `import_lookup` and `import_object_project` are invoker; `import_local_id`, `import_remember`, `import_member`, `import_date`, `import_timestamp` are revoked from clients; `anon` gains nothing.

## Bulk edit and shortcuts model

Migration `20261006010000_bulk_edit.sql`, tests in `supabase/tests/92_bulk_edit_smoke.sql`. No tables, no SECURITY DEFINER functions: everything runs as the caller, so RLS and every existing trigger apply exactly as for single edits. Generic: nothing knows about a team or request type.

### Bulk edit (`bulk_update_tasks`)

- `rpc("bulk_update_tasks", { target_tasks uuid[], operation jsonb })` (SECURITY INVOKER), called by `bulkEditTasks()` in `actions.ts`. Operations (mirrored by `src/lib/bulk.ts`): `complete`, `reopen`, `delete` (soft, to Trash), `assign {assignee_id | null}`, `set_due {due_on | null}`, `move_section {project_id, section_id | null}` (appends at the end of the section), `add_to_project {project_id, section_id?}` (multi-homes; re-activates a removed membership), `set_field {field_id, value}` (JSON null clears; a section-bound Status field is rejected — use `move_section`), and since Tags and collaboration extras `add_tag {tag_id}` (archived tags rejected) / `remove_tag {tag_id}`.
- **Limits and validation:** 1–200 distinct task ids (duplicates are dropped, order kept). Problems with the operation itself raise and change nothing: unknown action, a section of another project, a missing or section-bound field, a missing person, or no Editor role in the target project (`move_section`, `add_to_project`, and the field's project for `set_field` → `insufficient_privilege`).
- **Partial apply (Asana style):** each task runs in its own `begin … exception` block (a subtransaction), so a failure rolls back only that task, including any rule it fired. A task is **skipped with a reason** when it isn't readable (“Not found, or you don’t have access to it”, title `null` so nothing leaks), is in the Trash, the caller is below Editor on it (`has_task_role`), it is blocked by an incomplete predecessor (the dependency guard's message, e.g. “This task is blocked by 1 incomplete task”), the assignee can't read it (`profile_can_read_task` → “<Name> isn’t a member of this task’s projects”), its start date is after the new due date, or it isn't in the project/field's project. Other errors pass their message through `bulk_skip_reason()`.
- **Completing in dependency order:** tasks blocked only by other tasks in the same request are retried after each pass while the pass made progress, so completing a predecessor and its successor together works in any order.
- **Result:** `{ updated: [ids changed], unchanged: [already in that state — no write, no story], skipped: [{ task_id, title, reason }] }`. Stories, inbox items, and rules come from the normal row triggers, once per changed task, attributed to the caller.
- **UI:** `useTaskSelection` (List and My Tasks): checkbox toggles (Shift adds a range), row click selects one, Shift-click selects a range, ⌘/Ctrl-click toggles (also on the title link, instead of opening a new tab). Selection of tasks that disappear is dropped on render. `BulkBar` (bottom of the screen, Editors only in List): Complete / Reopen (shown by the selection's state), Assign (assign to me, unassign, or a person — the project's members in List, everyone in My Tasks), Due date (set / clear), Move (List: a section of this project), Add to project (projects where the viewer is Editor+), Field (List: non-section-bound fields; multi-select/people replace the whole value), Delete (confirm). A clean run toasts “Completed 8 tasks” (or “No changes”); any skip opens a summary (`role="alertdialog"`) listing each skipped task and why. My Tasks has no Move/Field (its tasks span projects).

### Ordering (`place_task`, `place_section`, reindex)

- `place_task(target_task, target_project, target_section, before_task)` (invoker; Editor on the project) sets the membership's section and a `sort_order` between `before_task` and the task above it (`null` = end of the section: max + 1024; first = next − 1024). When the gap is below `min_order_gap()` (1e-6) or the neighbour is tied, it calls `reindex_task_order(target_project, target_section)` (renumbers active memberships of that section 1024, 2048, … in current order, ties broken by created_at, task id) and recomputes. `place_section(target_section, before_section)` / `reindex_section_order(target_project)` do the same for sections. Section changes write `section_changed` stories and fire section rules like `moveTask`; pure reorders write nothing.
- The browser still computes the same midpoint (`sortOrderFor`) for the optimistic update; the database's answer wins on refresh. Board's manual-order drops use `placeTask` too.
- **List drag-and-drop:** rows are draggable only for Editors with manual sort + section grouping (drop on a row's upper/lower half, or anywhere in a section to append; collapsed sections accept drops on the header). Sections get a drag handle plus Move up / Move down buttons (keyboard path) when grouped by section with no section filter; a drop zone at the end moves a section last.

### Keyboard shortcuts

- **Never while typing:** `isTypingTarget()` (text inputs, textareas, selects, contenteditable) is checked first, and list shortcuts also stand down while any `role="dialog"` / `alertdialog` is open (popovers, the help overlay, the bulk summary).
- **Global** (`KeyboardShortcuts` in the app layout): `?` toggles the help overlay (lists every shortcut; ⌘ on Mac, Ctrl elsewhere); `/` focuses the sidebar search, or opens `/search` when the sidebar is hidden.
- **List and My Tasks** (`useListKeys`): ↑/↓ move the selection (Shift extends from the anchor; tasks in collapsed groups are skipped), Enter opens the selected task (on the page or a row — Enter on a focused button or link keeps its normal meaning), Esc leaves the pane to close itself, else clears the selection, ⌘/Ctrl+Enter completes the selection (or the open task, or the cursor task) and reopens if all are complete, **Tab then Q** opens the quick-add input in the cursor task's section (else the first section; List only), **Tab then M** assigns the targets to the viewer. Tab keeps moving focus as usual: the chord is Q/M within a second of Tab, with neither key pressed in a text field. Shortcuts go through the same RPC as the bar, so a viewer's ⌘+Enter shows “Your role doesn’t allow editing this task” in the summary.

## Templates model

Migration `20261006020000_templates.sql`, tests in `supabase/tests/93_templates_smoke.sql`. One copy engine, three features. Generic: the seeded example is the only named template, and nothing in the schema knows about a team or request type.

### Copy engine

- `project_snapshot(source_project, opts)` (SECURITY DEFINER, internal) turns a project into a versioned JSON snapshot (format documented at the top of the migration): project description + `approval_completes_task`, Req # settings (numbering restarts at 1, and copied tasks are numbered like any new task when the sequence numbers all tasks), sections, custom field definitions (option ids kept), forms, rules, saved views, tasks (section, `sort_order`, notes, field values, the full subtask tree — `snapshot_subtasks()` / `instantiate_subtasks()`: title, notes, kind, dates as offsets, field values, optional completion/assignee, nested — optional completion/assignee), dependencies between copied tasks, optional members. **Dates are day offsets** from `anchor_on` (given, else the earliest start/due date of the copied tasks): `due_offset`, `start_offset`, and date-field values as `{ field_id, offset }`. A task's `[Req #…] ` title prefix is stripped. Approval subtasks, comments, attachments, followers, approvals, times (`due_at` / `start_at`), and recurrence are never copied. The task **kind** is (snapshot key `kind`; older snapshots make plain tasks), and a copied approval task opens no request (copies are quiet; an editor asks from the pane). Max 2,000 tasks per copy.
- `instantiate_project_snapshot(snapshot, name, start_on, workspace, story_kind, story_data)` (SECURITY DEFINER, internal) creates a project owned by the caller and inserts everything in dependency order (members → Req # → sections → fields → forms → rules → views → tasks → dependencies). Offsets resolve as `start_on + offset`. Old section/field/form ids are mapped to the new rows and **rewritten by text replacement** in rule configs, form questions, and view configs (`template_remap()`; UUIDs make it exact, and `field:<uuid>` keys are covered). Rows that no longer validate are skipped and counted (forms, rules, views, field values) instead of failing the copy. Copied saved views replace the four default tabs when at least one copies. Forms land closed. Assignees and people values are kept only for people who are members of the new project. The caller is unfollowed from copied tasks not assigned to them. Returns `{ project_id, sections, fields, tasks, rules, rules_skipped, forms, forms_skipped, views, views_skipped, values_skipped, members }`.
- **Quiet copies (the importer's pattern):** `instantiate_project_snapshot` sets the transaction-local GUC `alhc.copy_id` (`copy_context_id()`), left set until commit. `fire_rules` and `notify_with` return early and `add_story` writes nothing while it is set (each keeps its import check exactly as it was, with the copy check after it), and `rules_04_copy_disabled` forces `enabled = false` on every rule inserted. **Every copied or templated rule lands disabled.** Instead of task stories, the copy writes **one `project_stories` row per created project** (`created_from_template` with the template id/name, or `duplicated` with the source id/name and options); project Settings → General shows it.
- **Integration secrets are never copied.** The snapshot strips `webhook_ref` / `webhook_hint` / `url_ref` / `url_hint` / `secret_ref` / `secret_set` from rule actions (so templates readable workspace-wide never carry a URL or secret), and `project_integrations` isn't copied; a copied Slack/webhook rule falls back to the new project's defaults or fails with the usual “no URL” error once enabled.

### Project templates (`project_templates`)

- `project_templates (id, workspace_id, name 1–100, description ≤ 2000, content (snapshot), summary (counts), source_project_id, is_example, created_by, …, deleted_at)`. **Workspace-level:** `project_templates_select_allowlisted` (everyone allowlisted sees and uses every template, like `rule_presets`); no client write grants — only the RPCs below write.
- `save_project_as_template(source_project, template_name, template_description, anchor_on, replace_template)` — **Admin+ on the source** (a template exposes the project's tasks and notes to the whole workspace, so the people who control the project's access decide). Templates carry no assignees, people values, members, or completion state; tasks and subtasks arrive incomplete. `replace_template` overwrites an existing template's content (needs `can_manage_project_template`, re-points `source_project_id`, clears `is_example`): this is how the team edits a template, the seeded example included.
- `create_project_from_template(target_template, project_name, start_on)` — anyone allowlisted (like creating a project); the caller owns the new project.
- **Managing (rename / replace / delete):** `can_manage_project_template(t)` = Admin+ of its **source project** while that project is active, **or a workspace admin** (since Workspace admin and comments; the old “Admin+ of any project” fallback is gone, so the seeded example is managed by workspace admins only). `update_project_template` (name/description) and `delete_project_template` (soft) check it.
- **Seeded example:** `Creative Requests` (`00000000-0000-4000-8000-0000000000c1`, `is_example`): sections Intake, In Progress, Review, Approved, Delivered; single-select fields Request type and Due date priority (no options); nothing else.

### Duplicate project

`duplicate_project(source_project, project_name, options)` — **Editor+ on the source**. ### Workload

- `project_workload(target_project, range_start, range_end, value_field)` and `portfolio_workload(target_portfolio, range_start, range_end, value_field_name)` (SECURITY INVOKER; `null` range ends are unbounded) return `(task_id, title, assignee_id, start_on, due_on, value, project_id, can_edit)` for **open, assigned tasks with a due date** whose span — `start_on .. due_on`, else the due day — overlaps the range. ## Critical path and portfolio depth model

Migration `20261006060000_critical_path_portfolios.sql`, tests in `supabase/tests/97_critical_path_portfolios_smoke.sql`. Generic: nothing knows about a team or request type. **Everything is SECURITY INVOKER except the trigger `guard_portfolio_child()`**, which must see every nesting link (including hidden ones) to reject cycles; like every definer trigger it is revoked from client roles, so suite 60's list is unchanged.

### Critical path (read-only)

- `project_critical_path(target_project)` (invoker; nothing for non-members) returns `(task_id, start_on, due_on, slack_days, critical, skipped)` for every active task of the project the caller can read. Tasks without a due date come back `skipped` (slack null) and the Timeline says how many. For the rest: start = `start_on` else `due_on` (a **milestone** always starts on its due day: zero length, since Task types and nested rollups); duration = due − start in days (a one-day task is 0); **finish** = the latest `due_on`; edges = active finish-to-start `task_dependencies` of this project between two dated tasks; **remaining** = the longest sum of successor durations along any chain from the task; **latest** = finish − remaining; **slack_days = latest − due_on**; **critical = slack ≤ 0**.
- A successor may start on its predecessor's due day (the Timeline's arrow rule), so a chain whose links all touch and that ends on the finish has zero slack — that chain is the critical path. Negative slack (“N days behind”) means a successor already starts before its predecessor is due. Completed tasks are part of the schedule like the rest.
- **No auto-scheduling:** nothing shifts successors; dates only change through the normal task edits.
- `projectCriticalPath()` in `data.ts` (cached per request) feeds the Timeline (`criticalPath` prop) and `TaskDetail.schedule` (one entry per task project, only when the task has a due date).

### Project status history (`project_status_updates`)

## Real subtasks model

Migration `20261006080000_real_subtasks.sql`, tests in `supabase/tests/99_real_subtasks_smoke.sql` (the data migration is checked against old-model rows from `supabase/tests/fixtures/before_20261006080000_real_subtasks.sql`). ### Shape

- A subtask is a `tasks` row with `parent_task_id` (a task or another subtask). `root_task_id` = the top-level task (null for ordinary tasks; CHECK: set exactly when there is a parent), `subtask_order` = order among siblings (fractional, step 1024). Everything a task has works on a subtask: assignee, start/due dates and times, notes, kind (milestone / approval), custom field values, comments, followers, attachments, approvals, recurrence, and its own subtasks.
- **Invoker trigger `tasks_05_subtask_parent`** (first BEFORE trigger) always recomputes `root_task_id`, `home_project_id`, and `workspace_id` from the parent (clients can't forge them, and the workspace is always the parent's). On insert or a parent change: the parent must exist (readable), be active, not be the task or one of its subtasks (**no cycles**), and the subtree must stay within **`subtask_max_depth()` = 4** levels below the top-level task (task → 1 → 2 → 3 → 4; a move counts the moved subtree's height, `subtask_height()`). A task can't become a subtask or a subtask a task yet (`check_violation`); since Reporting and export it also rejects, explicitly, a parent in another workspace (a client-sent `workspace_id` / `home_project_id` of another workspace on insert, or a new parent outside the subtask's workspace); a subtask can move under another parent (`place_subtask(target, before, new_parent)`, Editor on both trees).
- **Cascades** (invoker `tasks_cascade_subtasks`, one level per trigger): a new root or home project is copied down; trashing a task trashes its active subtasks with the same `deleted_at`, and restoring it restores exactly those. A subtask can't be restored while its parent is trashed (“Restore the parent task first”). Trash lists subtasks trashed on their own (parent active) whose root is in the project.
- **No memberships:** `ensure_home_membership` skips subtasks and `task_projects_05_no_subtasks` rejects adding one to a project (bulk “Add to project” / “Move” skip them with that reason). So `filter_project_tasks`, views, dashboards, the critical path, portfolio progress, goal progress, rules' `due_approaching`, and Timeline/Calendar/Board see top-level tasks only.

### Access

- `profile_task_role()` resolves the **root** (`coalesce(root_task_id, id)`) and reads its memberships; `task_role`, `has_task_role`, and `profile_can_read_task` are unchanged and inherit it. Policies on `tasks` use the row's own `root_task_id` (so `INSERT … RETURNING` and a reparent's WITH CHECK see the new values): select = Viewer+ of the root (Editor+ when trashed), insert = Editor+ of the root, update = Editor+ of `coalesce(root_task_id, id)` on both sides. Ordinary tasks keep exactly the previous rules.
- Field values: `validate_task_field_value` accepts fields of the **root task's** projects. Search labels a subtask with a project of its root. Workspace admins get nothing extra.

### Behaviour

- **Rules and Req # skip subtasks** in the calling triggers (`rules_on_task_update`, `rules_on_task_created`, `rules_on_field_value_change`, the `approval_decided` call in `on_approval_status_change`, `assign_request_number_on_insert`; `assign_request_number` refuses them). Subtasks never get a Req #.
- **Notifications** are the ordinary task ones (assigned, mention, comment, completed, approvals) through `notify_with` / `add_story`, so subtasks reach the assignee's Inbox and My Tasks (`my_tasks_layout()` places them like any assigned task). Workload (`project_workload` / `portfolio_workload`, same signatures) counts subtasks through their root's project membership.
- **Approval subtasks** are child tasks with no assignee (the approver's `approval_requested` on the parent is their one notification); a person can't tick one while its approval is open; approved / rejected complete it without extra `completed` items.
- **Copies:** project templates and Duplicate project carry full subtask trees (`snapshot_subtasks` / `instantiate_subtasks`; snapshot key `subtasks` = `[{ title, notes, kind, completed, completed_at, assignee_id, due_offset, start_offset, fields, subtasks }]`, older `[{ title, completed }]` snapshots still work; approval subtasks left out); recurrence copies the tree (`copy_subtask_tree`); task templates keep **titles** of direct subtasks; imports bring nested Asana subtasks (`import_subtasks`). All of it stays muted exactly like the rest of a copy / import (no rules, inbox items, or stories beyond the import's tagged `created`). These helpers are revoked from clients.

### Data migration

Every `public.subtasks` row became a child task with the **same id**, title, completion, `sort_order` → `subtask_order`, created/updated/deleted timestamps, root = parent = its task (user triggers off during the copy: no stories, inbox items, follows, numbers, or rules). `approval_requests.subtask_id` now references `public.tasks` (same ids, so links survive). `public.subtasks` stays as a retired table (comment says so; insert/update/delete revoked from clients; its old policies and guard trigger are left in place, inert).

### Dependencies: kind, lag, subtasks, cross-project

### Auto-shift (confirm, apply, Undo — all invoker)

- `rpc("preview_dependency_shift", { target_task, new_start_on, new_due_on })` → `(task_id, title, start_on, due_on, new_start, new_due, shift_days, status move | skipped, reason)` for the tasks that **would** move. Walks the caller-readable links from the task in topological order (longest path from it); a dependent is pushed only by a predecessor whose anchor (due for FS, start for SS) **moved later**, just enough to satisfy `anchor + lag`, keeping its length; moved tasks push their own dependents. **Moving earlier never pulls anything in.** Undated dependents have nothing to move. **Completed** dependents and dependents the caller **can't edit** are listed as `skipped` (with the reason) and don't move or push further; links to tasks the caller can't read are never followed, so the plan never names them.
- `rpc("apply_dependency_shift", { target_task, new_start_on, new_due_on, confirmed_tasks })` recomputes the plan against the current dates, moves the task (Editor required), then shifts **only the confirmed** `move` rows whose dates are still what the plan saw. Returns `{ changes: [{ task_id, title, old_start_on, old_due_on, new_start_on, new_due_on }] (the task first), skipped: [{ task_id, title, reason }] }`. Every update is a normal task update: RLS, `start_changed` / `due_changed` stories, rules, and times following their dates.
- `rpc("undo_dependency_shift", { changes })` puts each task back to its old dates **only while its dates are still the ones the shift set** (through RLS); anything changed since, unreadable, or not editable is reported in `skipped` (unreadable ones with a null title). `{ restored: [ids], skipped }`.
- **UI:** `useDependencyShift()` (`components/task/dependency-shift.tsx`) for Timeline drags, Calendar drags, and the pane's Start / Due dates: preview first; no dependent to move → a plain `updateTask`; otherwise a dialog lists **Will move** (checkbox each, old → new, +N days) and **Won't move** (reason), with **Move N dependents too** / **Only move this task** / **Cancel** — nothing else moves without that click. The transition (and the optimistic bar position) stays pending while the dialog is open. The result toast has **Undo** (toasts can carry one action now; they stay 12 s). Bulk “Due date”, Workload drags, rules, and recurrence don't auto-shift.

### HMAC body signing (`call_webhook`)

- **Secrets:** `integration_secrets` kind `signing_secret` — per project (`rule_id` null, one active row: `integration_secrets_project_signing_idx`; CHECK `integration_secrets_rule_check`) or per action (`signing_ref` + `signing_set: true` in `rules.actions`, stored by `rules_05_stash_integration_secrets` from a plain `signing_secret` key exactly like the shared secret; `""` removes it; 16–500 characters). - **Wire format** (drain, at send time, so each attempt has a fresh timestamp over the same stored body): `X-ALHC-Timestamp: <unix seconds>` and `X-ALHC-Signature: sha256=<hex HMAC-SHA256(key, "<timestamp>.<raw body>")>`. Signatures are never stored or logged.
- **Receiver verification** (documented in README “Setup: Slack and webhooks” with a Node snippet): read the **raw** body bytes before parsing; reject a missing or non-integer timestamp or one more than **300 seconds** (`SIGNATURE_TOLERANCE_SECONDS`) from the receiver's clock (stale-timestamp / replay rejection); recompute `sha256=` + hex HMAC over `"<timestamp>.<raw body>"`; compare in **constant time**; optionally drop repeats by `Idempotency-Key`. Re-serialising parsed JSON breaks the signature.

### Delivery log and retry

- **Retry policy:** a failed send returns to `pending` after `integration_retry_delay(attempts)` = 5, 10, 20, then 30 minutes (capped), until the row's `max_attempts` (default **5**), then `failed` + the redacted `integration_failed` story as before. `claim_integration_outbox` compares against `max_attempts` instead of a literal 5; `complete_integration_outbox` uses the delay. Retries reuse the stored target, headers, payload, and signing key; webhooks keep `Idempotency-Key: integration-outbox-<id>`.
- `list_integration_deliveries(target_project, max_results ≤ 200)` (**definer, Admin+**) → `id, channel, task_id, task_title (only when the caller can read the task), rule_id, rule_name, target_hint, status, attempts, max_attempts, response_status (the receiver's HTTP code), last_error (drain errors are already hint-only; any URL is masked again), signed, next_attempt_at (pending only), sent_at, created_at, updated_at` — **never** the URL, headers, payload, response body, secret, or signature.
- `retry_integration_delivery(target_delivery)` (**definer, Admin+**): a `pending` row is due now (“Send now”, same limit); a `failed` row goes back to `pending` with `max_attempts = attempts + 1` (one more attempt), **10 attempts in total at most** (`check_violation` after that). `cancel_integration_delivery` sets a `pending` row to `cancelled` (new status; never claimed). ## Inbound integrations model

Migration `20261007040000_inbound_integrations.sql`, tests in `supabase/tests/zz06_inbound_integrations_smoke.sql`. Free only (no paid services, no Slack app or OAuth). Generic: nothing knows about a team, tool, or request type. Everything else new is SECURITY INVOKER (the endpoint RPCs and guard trigger) or internal and revoked (`inbound_hmac_sha256`, `log_inbound_call`). Additive: the previous release keeps working once it is applied.

### Endpoints (`inbound_endpoints`)

- `(id, project_id, name 1–100, section_id?, assignee_id?, tag_ids uuid[] ≤ 20, enabled, token_hash (sha256 hex, unique), token_hint ('…' + last 4), token_rotated_at, signing_secret?, signing_secret_set_at?, created_by, created_at, updated_at, deleted_at)`. RLS `inbound_endpoints_select_admin` / `_insert_admin` (own `created_by`) / `_update_admin`, all `has_project_role(project, 'admin')` — **no `is_workspace_admin()` anywhere**, and an archived project caps everyone at Viewer, so its endpoints can't be managed. **Column grants:** clients select everything except `token_hash` and `signing_secret`, insert `(project_id, name, section_id, assignee_id, tag_ids, enabled, signing_secret_set_at)`, update `(name, section_id, assignee_id, tag_ids, enabled, token_rotated_at, signing_secret_set_at, deleted_at)`; nothing for anon.
- **Credentials are generated, never chosen.** The invoker guard `inbound_endpoints_05_guard` (`guard_inbound_endpoint()`) runs before every insert / update: forces `created_by` / `created_at` on client inserts, keeps endpoints from moving or coming back after delete, checks the section (this project), default assignee (an active member), and tags (active, unarchived, same workspace), and generates `alhc_in_` + 64 hex (`inbound_random_hex()`: two `gen_random_uuid()`s, 244 random bits) on insert or whenever `token_rotated_at` changes, and `whsec_` + 64 hex when `signing_secret_set_at` is set (null removes the secret). The plain values go back **once** through the transaction-local settings `alhc.inbound_token` / `alhc.inbound_signing_secret`, which the invoker RPCs read and clear: `create_inbound_endpoint(target_project, endpoint_name, target_section, default_assignee, default_tags, with_signing_secret)` → `{ id, token, signing_secret }`, `rotate_inbound_token(target_endpoint)` → `{ token }` (the old one stops at once), `set_inbound_signing_secret(target_endpoint, enable)` → `{ signing_secret }`. Below Admin they raise `insufficient_privilege` (create) or `no_data_found` (RLS hides the row). Name / section / assignee / tags / on-off / delete are ordinary updates (`updateInboundEndpoint`, `deleteInboundEndpoint`).

### Receiving (`receive_inbound_webhook`)

- `receive_inbound_webhook(endpoint_token, raw_body, request_timestamp, request_signature, idempotency_key) → jsonb { ok, status, task_id?, duplicate?, request_label?, warnings?, error? }`, called by `src/app/api/inbound/[token]/route.ts` with a cookie-less anon client (`/api/inbound` is a public path in the proxy). The route reads ≤ 64 KB of strict UTF-8 (so the database hashes exactly the signed bytes), passes `X-ALHC-Timestamp`, `X-ALHC-Signature`, and `Idempotency-Key`, and maps `status` to the HTTP status.
- **Order of checks:** token format → endpoint by `inbound_token_hash(token)` (active, enabled, project not deleted) → per-endpoint transaction advisory lock → **signature** when the endpoint has a secret (integer timestamp within **300 s** of the server clock; `sha256=<64 hex>` compared to `inbound_hmac_sha256(secret, "<ts>.<raw body>")` — RFC 2104 over core `sha256()`, no extension) → **rate limit** (60 logged calls a minute per endpoint → 429, one `rate_limited` row a minute) → **creator check** (`profile_is_allowlisted` and `profile_project_role` ≥ Editor; an archived project caps it at Viewer) → `Idempotency-Key` (1–200 printable characters; a key that already created a task returns that task, 200, `duplicate: true`, and creates nothing) → **replay** (`replay_digest` = sha256 of endpoint, timestamp, signature; a signature works once) → size (64 KB → 413) → JSON object (400) → validation (422: `title` 1–500, `notes` ≤ 20,000, `due_on` a real `YYYY-MM-DD`, `assignee_email` string, `tags` ≤ 20 names, `fields` ≤ 50).
- **Generic 401:** an unknown, malformed, disabled, deleted, or rotated-out token, a missing / wrong / stale / replayed signature, and a creator without access all return exactly `{ ok: false, status: 401, error: "Unauthorized" }`, so no answer confirms that a token exists. Unknown tokens are never logged; failures on a real endpoint are logged (`rejected`, with the reason) for its admins, but signature failures past the rate limit aren't (no log flooding).
- **The task** is a normal creation **as the endpoint's creator**: `request.jwt.claim.sub` is set transaction-locally for the writes (so `created_by`, stories, follows, and inbox items name the creator) and restored before rules fire; the whole creation runs in a subtransaction, so a failure rolls it all back (the impersonation setting included) and logs `failed` / 500. `source = 'inbound'`, home project = the endpoint's, section = the endpoint's (or a section-bound Status field value), assignee = `assignee_email` when that person is an active member, else the endpoint default (still a member), tags = the endpoint defaults plus payload names (active, unarchived workspace tags; unknown ones skipped), custom field values by **field name** (text, number, date, boolean, single-select option name, multi-select names, people by member email; values that don't fit are skipped). Unmatched references and unknown keys come back as `warnings` (never echoing values). Req # numbering applies; the creator is unfollowed unless they are the assignee (like the importer); an `inbound_received` story (`endpoint_id`, `endpoint_name`, `call_id`); then `fire_rules('inbound_received', …)` (plus `task_created` at commit). Imports and copies never reach this path, and `fire_rules` still returns early for them.

### Call log (`inbound_calls`)

`(id, endpoint_id, project_id, status created | duplicate | rejected | invalid | rate_limited | failed, http_status, task_id?, error ≤ 500, warnings jsonb, idempotency_key?, replay_digest?, created_at)`, written only by `log_inbound_call()` inside the receiver. RLS `inbound_calls_select_admin`; column grant excludes `replay_digest`; no client writes; nothing for anon. **Never the body, token, signature, or secret** (pinned; no column is named like `signature`). Settings → Inbound shows the latest 100 with the created task (title only when the viewer can read it).

### Rules

`inbound_received { endpoint_id? }` (“Created by inbound webhook”; `validate_rule` requires an active endpoint of the rule's project, so a copied rule naming another project's endpoint is skipped by the copy engine) and `source_is { source: "inbound" }`. The builder lists the project's endpoints (Admin+). Rules of archived projects never fire, and inbound calls to them are refused anyway.

### App

- `data.ts`: `listInboundEndpoints(projectId)` (with the last call time), `listInboundCalls(projectId)`. `actions.ts`: `createInboundEndpoint` (returns the token / secret once), `updateInboundEndpoint`, `deleteInboundEndpoint`, `rotateInboundToken`, `setInboundSigningSecret`.

## Conventions

- Server Components fetch via `src/lib/data.ts`; Client Components mutate via `src/lib/actions.ts` wrapped in `useServerAction()` (toasts errors, supports optimistic updates).
- Route params/searchParams are Promises (`await params`). Use `PageProps<"/route">` / `LayoutProps<"/route">` global types.
- Schema changes: add a new timestamped file in `supabase/migrations/`, update `database.types.ts` (or run `npm run db:types`), extend or add a `supabase/tests/NN_<area>_smoke.sql` suite (`10_core_smoke.sql`, `20_collaboration_smoke.sql`, `30_workflows_smoke.sql`, `40_views_insights_smoke.sql`, `50_timeline_smoke.sql`, `60_teams_permissions_smoke.sql`, `70_task_depth_smoke.sql`, `80_portfolios_smoke.sql`, `90_integrations_smoke.sql`, `91_asana_import_smoke.sql`, `92_bulk_edit_smoke.sql`, `93_templates_smoke.sql`, `94_workspace_admin_comments_smoke.sql`, `95_my_tasks_workload_smoke.sql`, `96_goals_teams_smoke.sql`, `97_critical_path_portfolios_smoke.sql`, `98_task_types_rollups_smoke.sql`, `99_real_subtasks_smoke.sql`, `zz01_reporting_export_smoke.sql`, `zz02_tags_collaboration_smoke.sql`, `zz03_scheduling_polish_smoke.sql`, `zz04_daily_essentials_smoke.sql`, `zz05_integration_depth_smoke.sql`, `zz06_inbound_integrations_smoke.sql`, `zz07_review_hardening_smoke.sql`, `zz08_email_live_smoke.sql`, `zz09_asana_feel_1_smoke.sql`, `zz10_asana_feel_2_smoke.sql`, `zz11_asana_parity_1_smoke.sql`, `zz12_asana_parity_2_smoke.sql`, `zz13_asana_parity_4_smoke.sql`, `zz14_asana_parity_5_smoke.sql`, `zz15_real_1_smoke.sql`), run `npm run db:test`. Suites run in lexical filename order, so a new suite must sort after the last one. `99_real_subtasks_smoke.sql` is the last two-digit name: **after `99_` come `zz01_`, `zz02_`, … (two digits; `zz01_`–`zz15_` are taken, so the next suite is `zz16_`)**, which sort last in both C and locale order; never `100_…` or `991_…` (they sort before `10_` / among the `99_` names). A suite that must check a data migration against old-model rows can add `supabase/tests/fixtures/before_<migration file name>`, which `run.sh` loads just before that migration (write it with triggers off, `session_replication_role = replica`, and keep it consistent with the old schema). Suites that act as a second person must give them a project or portfolio membership first (`add_project_member` / `add_portfolio_member`).
- New project-scoped tables: RLS with `<table>_<command>_<role>` policies via `has_project_role` / `has_task_role` (pick the lowest role from the matrix that should have the capability), soft delete, no DELETE policy. Portfolio-scoped tables use `has_portfolio_role`, and anything that exposes project data through a portfolio must also check `has_project_role(project, 'viewer')`. Don't add new `_allowlisted` policies to project data.
- Task filters (views, dashboard widgets, and anything new that needs "tasks matching X") go through `filter_project_tasks` and the one config schema in the views migration + `src/lib/views.ts`. Extend that schema (validators, parser, and smoke tests together) instead of adding a second filter format.
- Changing an existing function: prefer an **asserted text patch** of its live definition (the `alhc_patch_function(regprocedure, old, new, …)` helper: each `old` must match exactly once, every other line stays, grants are kept) over pasting the whole function again. **Since Inbound integrations the helper stays on the hosted project:** a migration that needs it starts with `create or replace function public.alhc_patch_function(…)` followed by `revoke all on function public.alhc_patch_function(regprocedure, text[]) from public, anon, authenticated;`, and **never drops it** at the end (that drop kept timing out through the Supabase connector). Older migrations up to Inbound integrations still drop it; that's history, don't copy it. (Since Email live the older suites only check that the helper, when present, is not executable by clients.)
- **No row-removal or object-removal keywords before the tail.** The hosted connector refuses any statement that contains `DROP` or `DELETE` as a word, function bodies and comments included. Write everything above a final **TAIL** section without them (no `on delete …` clauses, `revoke all` instead of naming the privilege, prose like “remove” in comments), and put the statements that genuinely need one in that tail, which nothing above may depend on. The migration-applier applies everything before the tail; the tail is applied by hand (Avi / Grok Bot), and the PR merges only after `list_migrations` shows it.
- Trigger functions that write on the user's behalf are `SECURITY DEFINER` with `set search_path = ''`, and their helpers are revoked from `public`, `anon`, and `authenticated`. Revoke EXECUTE on every new SECURITY DEFINER **trigger** function too (Supabase's default privileges grant it to `anon`/`authenticated`; triggers fire regardless). The timeline migration revoked it from all existing ones, and `50_timeline_smoke.sql` asserts that `anon` can execute no SECURITY DEFINER function except `get_public_form`, `submit_form`, and `receive_inbound_webhook` (three, since Inbound integrations; since Review hardening `zz07_review_hardening_smoke.sql` also pins those three as the **only** functions of any kind anon can execute in `public`; the one exception outside `public` is `alhc_storage.form_upload_allowed`, the Storage policy helper of Real features 1, pinned by `zz15_real_1_smoke.sql`). `60_teams_permissions_smoke.sql` pins the exact SECURITY DEFINER list `authenticated` can execute: adding a client RPC means adding it there on purpose.
- **New ALHC tables and functions revoke anon** (Review hardening). Supabase's default privileges grant every new table and function in `public` to `anon`, and the schema is shared with Isaiah Approval, so the schema's default privileges stay as they are; instead, the migration that creates a table runs `select public.alhc_revoke_anon_grants(array['<table>']);` (or `revoke all on public.<table> from anon;`), and one that creates a function runs `select public.alhc_revoke_anon_execute(array['<name>(<arg types>)']);` (or revokes EXECUTE from `public, anon` itself and grants `authenticated` what it needs). Only `get_public_form`, `submit_form`, and `receive_inbound_webhook` are ever executable by anon in `public` (a Storage policy helper anon must evaluate goes in the unexposed `alhc_storage` schema instead, like `alhc_storage.form_upload_allowed`), and no ALHC table is ever readable or writable by anon (RLS is not the only wall). `zz07_review_hardening_smoke.sql` fails on any table or function that keeps an anon grant.
- Keep the UI restrained: zinc neutrals, one accent (`accent-*` in `globals.css`), no gradients, accessible labels on every control (icon-only buttons: an `aria-label` plus a `data-tooltip`). Reuse the Redesign tokens and components (`h-bar`, `h-row`, `px-gutter`, `btn-*`, `control`, `chip`, `PageHeader`, `EmptyState`, skeletons, `pane-styles.ts`, `view-chrome.tsx`) instead of one-off spacing and button classes; every list, tab, and page needs an empty state that says what goes there and how to start.

## Shipping a phase (apply, then merge)

The hosted Supabase project **`xsgmawawwstbrbukgsax` is shared with another app (Isaiah Approval)**: its tables and migrations are not ours. Since Integration depth a phase ships like this — the migration goes in **before** the merge, so the code Vercel deploys from `main` never runs against a schema that lacks it. That is why every migration must be **additive**: the production code still on `main` has to keep working once it is applied.

1. Branch from the latest `main`; build the phase with one new migration file and one new smoke suite.
2. `npm run lint`, `npm run typecheck`, `npm run build`, and `npm run db:test` (all suites) must pass.
3. Open the PR titled `Phase: <name>` and wait until every check passes.
4. **Always hand the apply step to the `migration-applier` subagent** (`.claude/agents/migration-applier.md`) — the main agent never calls `apply_migration` itself. Give it the phase's migration file path and slug (e.g. `supabase/migrations/20261007030000_integration_depth.sql`, `integration_depth`). It splits the file at statement boundaries only (never inside a dollar-quoted body; each function keeps its revoke / grant), proves the chunks join back byte-identical, and applies them in order as `<slug>_a`, `<slug>_b`, … on `xsgmawawwstbrbukgsax`. If some `<slug>_*` chunks are already recorded (a partial earlier apply), it skips those and continues with the rest; it stops only when the recorded names aren't a contiguous run from `_a`. On a failure or timeout it waits 60 seconds, checks `list_migrations`, and retries that chunk once only if it isn't recorded; a second failure stops it. It runs no other SQL and never touches `supabase/tests`. Chunk markers in the migration file are not needed.
   If the file has a **`-- TAIL`** line (statements with `DROP` / `DELETE` after it), the subagent applies only what comes before it and stops. Report the tail to Avi, wait for them to say it's applied, verify with `list_migrations`, then merge. Never retry, loop on, or disguise those statements.
5. Read its report. If any chunk wasn't applied, or the subagent or connector isn't available, stop **without merging** and report.
6. Only after every chunk is applied, **squash-merge** the PR, and confirm Vercel production is Ready for the merge commit when that can be checked.

**Never** apply anything under `supabase/tests`, run other SQL on the hosted project, reset / branch / drop / clean up the hosted project, or touch the other app's tables or migrations; never change Auth (Site URL, redirects, Google, SMTP) or the allowlist from a phase. Never weaken the import / copy checks in `fire_rules`, `notify_with`, `notify_message`, or `add_story`, and never let a workspace admin bypass project or private-task access.
